# Внутренние структуры данных Typesense и влияние настроек поиска

Typesense — поисковый движок in-memory (с персистентностью на диск), построенный на нескольких структурах данных. Ниже — как они устроены и как настройки поиска влияют на их поведение.

## 1. Основные структуры данных

### Инвертированный индекс (Inverted Index)
Для каждого токена хранится postings list — список документов, где он встречается, с позициями и частотами. Используется для полнотекстового поиска.

- Поля `query_by` определяют, какие инвертированные индексы строятся (по каждому полю).
- `token_separators`, `symbols_to_index` влияют на токенизацию → какие токены попадают в индекс.
- `num_typos` → при поиске строятся дополнительные варианты токенов (fuzzy), что увеличивает обход postings lists.

### Префиксное дерево (Trie / Radix Tree)
Используется для префиксного поиска (`prefix: true`) и автодополнения. Хранит префиксы токенов и ссылки на postings.

- Включение `prefix` увеличивает нагрузку на trie (больше путей).
- Длинные запросы → больше узлов trie обходится.

### Skip Lists / Roaring Bitmaps
Для фильтров (`filter_by`) и фасетов (`facet_by`) Typesense использует bitmap/roaring structures для быстрого пересечения множеств документов.

- `filter_by=category:=Кино` → пересечение bitmap категории с postings запроса.
- `facet_by` строит агрегации по bitmap-полям.

### Сортировочные структуры (Sort Index)
Для `sort_by` (например, `date:asc`) поддерживаются отсортированные индексы (skip-list/array) по полю, позволяющие быстро получать топ-N.

- Поле должно иметь `sort: true` в схеме.
- Комбинированная сортировка (`date:asc,_text_match:desc`) требует слияния нескольких порядков.

### Векторный индекс (HNSW — Hierarchical Navigable Small World)
Для `float[]` полей (embedding) строится HNSW-граф для приближённого поиска ближайших соседей (ANN).

- `num_dim` фиксирует размерность векторов.
- `vector_query: embedding:([..], k:N)` обходит HNSW-граф, возвращая N ближайших.
- Параметры HNSW (M, efConstruction, efSearch) влияют на точность/скорость; в Typesense настраиваются через параметры коллекции/запроса (`ef_search`).

### Документное хранилище (Doc Store)
Исходные документы хранятся в row-store для выдачи (`retrieve`), независимо от индексов.

## 2. Как настройки поиска влияют на структуры

### `query_by` и `query_by_weights`
- Определяют, по каким инвертированным индексам идёт поиск и с каким весом. Больше полей → больше индексов обходится, выше recall, ниже скорость.

### `num_typos`
- 0: точное совпадение токенов (только postings).
- 1/2: генерация fuzzy-вариантов (Levenshtein) → дополнительные обходы индекса, выше recall, ниже точность.

### `prefix`
- true: обход trie по префиксу → автодополнение, больше кандидатов.

### `filter_by`
- Пересечение bitmap фильтра с postings → сужение кандидатов до фильтра.

### `sort_by`
- Если поле в sort-индексе → быстрый топ-N.
- Иначе сортировка в памяти по документам.

### `per_page` / `page`
- Влияет на объём данных, извлекаемых из doc store и индексов.

### `max_candidates` / `search_cutoff`
- Ограничивает число кандидатов из индекса → ускоряет, но может снизить recall.

### Векторный поиск (`vector_query`)
- HNSW traversal с параметром `k` (число соседей) и `ef` (ширина поиска).
- Больше `ef` → выше recall/точность, ниже скорость.

### `exclude_fields` / `include_fields`
- Влияет только на выдачу из doc store, не на индексы.

## 3. Практические следствия для приложения school_events

- Добавление поля в `query_by` расширяет инвертированные индексы → больше совпадений.
- `sort_by: date:asc` использует sort-индекс по `date` (sort:true) → быстрая хронологическая выдача.
- `filter_by: category:=Кино` → bitmap-пересечение → быстрый отбор.
- Векторный поиск по `embedding` → HNSW → семантически близкие события.
- `num_typos=1` помогает при опечатках в запросах (например, «выставка» → «выстовка»).

## 4. Баланс скорость/качество

- Больше полей в `query_by`, выше `num_typos`, `prefix:true`, больше `ef` → выше recall/качество, ниже скорость и выше память.
- Ограничение `max_candidates`, уменьшение `per_page`, точные фильтры → выше скорость.

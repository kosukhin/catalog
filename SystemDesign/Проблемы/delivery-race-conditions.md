# Доставка заказов разными способами: проблема и гонки (race conditions)

> **Область документа.** Здесь описана **только проблема**: предметная область, участники, жизненный
> цикл заказа, способы доставки, ресурсы, за которые конкурируют участники, и полный перечень
> **race conditions**, которые в этой системе возникают. **Решения, подходы, паттерны и «как надо
> сделать правильно» здесь намеренно не рассматриваются** — это отдельный документ.

---

## 1. Контекст: что за система

Маркетплейс + собственная логистика «Склад-Онлайн».

| Параметр | Значение |
|---|---|
| Заказов в сутки | ~120 000, из них 40% в вечерний пик 18:00–22:00 |
| Одновременных пользователей в пик | ~35 000 |
| Складов / дарксторов | 12 (у каждого свой физический сток) |
| Своих курьеров | ~900, партнёрских ~2 500 |
| ПВЗ (пунктов выдачи) | 640 |
| Постаматов | 1 200 (ячейки S / M / L) |
| Способов доставки | 6 (курьер, экспресс, ПВЗ, постамат, самовывоз, межгород — см. §2) |
| Внешних интеграций в потоке заказа | платёжный провайдер, WMS, служба курьерской доставки, транспортная компания (межгород), SMS/push, 1С |

### 1.1. Участники

- **Клиент** — web / мобильное приложение. Может оформлять заказ, менять адрес и слот, отменять, подтверждать получение, оформлять возврат.
- **Склад / WMS** — резервирует и собирает товар, взвешивает, печатает накладные, отгружает.
- **Даркстор** — точка экспресс-сборки для доставки «за 2 часа» и для самовывоза.
- **Курьер** — подтверждает «взял», «доставил», может отказаться от заказа.
- **ПВЗ** — принимает посылку на полку, выдаёт клиенту, хранит 7 дней, возвращает невостребованное.
- **Постамат** — принимает посылку в **конкретную ячейку определённого размера**, хранит 2 суток.
- **Транспортная компания (ТК)** — межгород, присылает статусы вебхуками, у неё свои трек-номера.
- **Платёжный провайдер** — холдирование и списание, присылает вебхуки, умеет ретраить их часами.
- **Служба поддержки** — операторы вручную отменяют заказы, меняют адреса, инициируют возвраты.
- **Планировщики / воркеры** — фоновые задачи: истечение сроков хранения, переназначение курьера, автозакрытие заказа, пересчёт маршрута.

### 1.2. Из чего собран поток заказа

```
client ──► order-service ──► payment-service ──► payment provider
                │                   │
                │                   └─ вебхук «оплачено» ◄── (ретраи, дубли)
                ├──► inventory-service ──► WMS (резерв, сборка)
                ├──► slot-service (курьерские слоты)
                ├──► locker-service (ячейки постаматов)
                ├──► pvz-service (места на полках ПВЗ)
                ├──► delivery-orchestrator ──► курьерская служба / ТК
                │                                └─ вебхуки статусов (дубли, порядок не гарантирован)
                └──► notification-service (SMS/push, тоже с ретраями)
```

Общие свойства этой схемы, важные для понимания проблемы:

- **Несколько инстансов** каждого сервиса (автоскейл, 3–20 реплик), в том числе **несколько экземпляров планировщиков**.
- **Асинхронные очереди** с доставкой **at-least-once** (событие может прийти дважды и в любом порядке).
- **Нет распределённых транзакций** между сервисами и внешними системами: только локальные транзакции в каждой БД + саги/компенсации, которые сами по себе не мгновенны.
- **Кэши** (Redis) перед статусами заказа, остатками, тарифами, занятостью ячеек.
- **Ретраи** на всех границах: клиент, шлюзы, воркеры, вебхуки провайдеров.
- **Ручные действия** операторов поддержки в тех же данных, где работают автоматические процессы.

## 2. Ключевая особенность задачи

**Один и тот же заказ проходит через несколько независимо управляемых ресурсов, и каждый способ доставки
«захватывает» свой ресурс, но все они конкурируют за один физический товар.**

| Способ доставки | Что резервируется в момент оформления | Кто подтверждает | Лимит / ёмкость | Срок жизни резерва |
|---|---|---|---|---|
| Курьер до двери | слот времени (интервал 2 ч) в зоне | диспетчер → курьер | N заказов на слот | до доставки |
| Экспресс 2 ч из даркстора | слот + единица товара в дарксторе | курьер | жёсткое окно 120 мин | 2 ч |
| ПВЗ (пункт выдачи) | место на полке пункта | ПВЗ | 60–400 мест | 7 дней |
| Постамат | **ячейка конкретного размера** | постамат | фиксированное число ячеек S/M/L | 2 суток |
| Самовывоз из магазина | единица товара на конкретном магазине | сотрудник магазина | сток магазина | 3 дня |
| Межгород (ТК) | место в машине/контейнере + трек-номер | ТК | тарифная сетка | до 14 дней |

Отсюда три источника конфликтов:

1. **Физический товар общий** для всех способов: одна и та же последняя единица может быть одновременно
   нужна курьерскому заказу, самовывозу и межгороду.
2. **Ёмкостные ресурсы дискретны**: слот, полка, ячейка — их нельзя «немного переполнить».
3. **Статус заказа приходит из нескольких независимых источников** (WMS, курьер, ПВЗ, постамат, ТК,
   платёжный провайдер, оператор поддержки), и эти источники не синхронизированы между собой.

## 3. Жизненный цикл заказа и два независимых статуса

```
CREATED ──► AWAITING_PAYMENT ──► PAID ──┬──► RESERVED ──► ASSEMBLING ──► ASSEMBLED ──┐
              │                          │                                            │
              │                          └──► RESERVE_FAILED ──► CANCELLED            │
              └──► PAYMENT_EXPIRED                                                     │
                                                                                       ▼
     ┌──────────────────────────── HANDED_TO_DELIVERY ──► IN_TRANSIT ──┐   READY_FOR_PICKUP
     │                                                                 │            │
     ▼                                                                 ▼            ▼
 DELIVERED / PICKED_UP ──► CLOSED                       NOT_PICKED_UP ──► RETURNING
                                                                              │
                                            LOST / DAMAGED ──► CLAIM ◄───────┘
```

Параллельно живёт **второй статус — статус доставки**, которым управляет не order-service, а
delivery-orchestrator и внешние системы (курьер, ПВЗ, постамат, ТК). Эти два статуса:

- обновляются разными сервисами в разные моменты времени;
- приходят через **at-least-once** очередь (дубли и переупорядочивание);
- **не имеют общего порядка событий** (у ТК «доставлено» может прийти раньше, чем «принято в сортировочном центре»);
- доступны клиенту ещё и через кэш, который обновляется отдельно от БД.

Именно это расхождение «статус заказа ≠ статус доставки» — питательная среда для большинства гонок ниже.

## 5. Гонки подробно

### RC-1. Двойная продажа последней единицы товара (oversell между способами доставки)

**Участники:** клиент A (курьер), клиент B (самовывоз), inventory-service (2 реплики), WMS.

**Раскадровка:**

```
Остаток товара X на складе №3 = 1 шт. (read: available = 1)

T1  Клиент A: «зарезервируй 1 шт для курьерской доставки»     -> instance #1
T2  Клиент B: «зарезервируй 1 шт для самовывоза»              -> instance #2
T3  instance #1: SELECT available -> 1, 1 >= 1, ок
T4  instance #2: SELECT available -> 1, 1 >= 1, ок
T5  instance #1: INSERT reservation(A, X); UPDATE available = 0
T6  instance #2: INSERT reservation(B, X); UPDATE available = 0   <-- потерянное обновление
```

Между «прочитал остаток» и «записал резерв» нет атомарности: **проверка и запись разделены**. При этом
резервы создаются в разных подсистемах (курьерская — через склад, самовывоз — через сток магазина),
поэтому проверка остатка и списание идут над **разными представлениями одного и того же физического товара**.

**Усугубляющие обстоятельства:**

- Остаток кэшируется в Redis на 30 секунд → два запроса читают одно и то же устаревшее «1 шт».
- Часть стока «в пути» между складом и даркстором: в двух местах товар одновременно числится доступным.
- При разделении заказа на несколько отправлений одно отправление резервируется, а второе — нет, и заказ
  остаётся в подвешенном состоянии.
- Отмена клиента A освобождает резерв, но только через 15 минут — всё это время товар не продаётся,
  а B уже получил отказ.

**Как проявляется:** клиент оплатил заказ, через 2 часа получает «товара нет, отменяем»; на складе при
сборке не хватает 1 шт; в отчёте остатков отрицательное значение; два клиента приехали за одним товаром
в один и тот же магазин.

**Как это заметно (симптомы в данных):** `available < 0` в снапшотах остатков, доля отмен по причине
`OUT_OF_STOCK` выше базовой в пик, расхождение между числом резервов и списаний в WMS.

### RC-2. Двойное оформление заказа (double submission)

**Участники:** клиент (мобильное приложение), order-service (N реплик), payment-service, платёжный провайдер.

**Раскадровка — два независимых сценария, дающих один результат:**

```
Сценарий «двойной клик» (плохая сеть, кнопка не дала визуальной реакции):
T1  POST /orders #1 ──► order-service #1: создал заказ 1001
T2  POST /orders #2 ──► order-service #2: создал заказ 1002   (та же корзина, тот же клиент)
T3  оба заказа идут в оплату -> два списания -> два резерва -> две доставки
```

```
Сценарий «ретрай шлюза»:
T1  POST /orders ──► order-service: заказ 1001 создан, ответ не дошёл (таймаут 5с)
T2  клиентский шлюз ретраит тот же запрос
T3  order-service #2: заказ 1002 создан (запрос ничем не отличается от первого)
```

**Что именно ломается:** у запроса на создание заказа нет признака «это тот же самый запрос» —
ни на уровне транспорта, ни на уровне бизнес-ключа. Поэтому любой ретрай (клиент, шлюз, балансировщик,
вебхук от платёжной страницы) порождает **новую сущность**, а не повторное чтение старой.

Дополнительно накладывается платёжная часть: страница оплаты может прислать подтверждение **дважды**
(пользователь вернулся назад и оплатил снова), и оба подтверждения привязываются к разным заказам, потому
что «корзина» к этому моменту уже переиспользована.

**Как проявляется:** в поддержку приходят «списали дважды»; на складе две одинаковые посылки на один адрес;
курьер привозит два одинаковых заказа; клиент отменяет один — второй продолжает ехать.

**Симптомы:** два заказа с одинаковым составом корзины, созданные в пределах нескольких секунд одним
клиентом; пары `payment_id` на один и тот же `cart_id`.

### RC-3. Гонка за последний курьерский слот (переполнение ёмкости)

**Участники:** клиенты, slot-service, диспетчер, курьер.

**Раскадровка:**

```
Слот «завтра 18:00–20:00, зона Север», capacity = 10, occupied = 9

T1  Клиент A: GET /slots -> занято 9, свободно 1
T2  Клиент B: GET /slots -> занято 9, свободно 1
T3  A: POST /orders/{id}/slot -> проверка 9 < 10 -> UPDATE occupied = 10
T4  B: POST /orders/{id}/slot -> проверка 9 < 10 -> UPDATE occupied = 10   <-- lost update
```

Счётчик занятости читается и увеличивается не атомарно. Дополнительные слои:

- клиент держит слот, пока заполняет форму: резерв слота живёт отдельно от заказа и может протухнуть
  или, наоборот, не освободиться при отмене;
- диспетчер вручную «докидывает» заказы в слот, не сверяясь с тем же счётчиком;
- экспресс-заказы «за 2 часа» вклиниваются в тот же интервал, но считаются по другой ёмкости;
- при отмене заказа слот освобождается асинхронно, и в окне между отменой и освобождением ёмкость занижена.

**Как проявляется:** в слоте 12 заказов на 10 мест; курьер физически не успевает; часть заказов переносится
на следующий день уже после оплаты; клиенты получают «ваш заказ задерживается» в день доставки.

**Симптомы:** `occupied > capacity` по слоту; «хвост» заказов в конце интервала у одного курьера; рост
`DELIVERY_DELAYED` в конкретных зонах.

### RC-4. Одна ячейка постамата достаётся двум заказам

**Участники:** locker-service, постамат (устройство), курьер-закладчик, два заказа.

**Раскадровка:**

```
Постамат PS-441, свободные ячейки размера M: {17, 22}

T1  Заказ A (нужна ячейка M): читает список ячеек -> 17
T2  Заказ B (нужна ячейка M): читает тот же список -> 17
T3  A: UPDATE cell 17 SET state='RESERVED', order=A
T4  B: UPDATE cell 17 SET state='RESERVED', order=B   <-- перезапись (lost update)
T5  Курьер с посылкой A открывает 17 -> внутри уже посылка B (или наоборот)
```

**Особенности именно постамата:**

- ячейка — физический объект, «создать ещё одну» нельзя; размеры S/M/L не взаимозаменяемы (заказ, которому
  нужна L, не влезает в M), а свободных S может быть много при нуле свободных M;
- состояние ячейки живёт в двух местах — в locker-service и в самом устройстве; устройство бывает офлайн,
  и тогда БД и «железо» расходятся до следующей синхронизации;
- курьер-закладчик работает по списку «что в какую ячейку», который мог устареть;
- клиент не забрал посылку → ячейку освобождает фоновый процесс, который может отработать дважды или
  не отработать вовсе;
- при переполнении постамата заказ переносится в соседний, и старое назначение ячейки не всегда снимается.

**Как проявляется:** курьер не может закрыть ячейку («занято»); клиент открывает ячейку и находит чужую
посылку; посылка физически лежит в ячейке, но в системе она «свободна», и туда кладут вторую.

**Симптомы:** два заказа с одинаковым `cell_id`; расхождение `cell.state` в БД и фактического состояния;
ячейки в `RESERVED` без активного заказа.

### RC-5. Переполнение полки ПВЗ

**Участники:** pvz-service, оператор ПВЗ, WMS, планировщик перевозок между складом и ПВЗ.

**Раскадровка:**

```
ПВЗ «Тверская-14», мест на полке = 60, занято = 59

T1  order #1 (перевозка в ПВЗ) -> проверка 59 < 60 -> место занято (60)
T2  order #2 (перевозка в ПВЗ) -> проверка 59 < 60 -> место занято (60)  <-- lost update
T3  order #3 (перевозка в ПВЗ) -> проверка 59 < 60 -> место занято (60)
```

Дополнительные слои проблемы:

- место занимается **в момент оформления заказа клиентом**, а физически посылка приезжает через 1–3 дня;
  за это время лимит меняется (ПВЗ приостановил приём, часть полок закрыли на ремонт);
- выдача освобождает место, но событие выдачи идёт через очередь — счётчик отстаёт от реальности;
- невостребованные посылки уходят в возврат по таймеру; если таймер сработал дважды, место освобождается
  дважды и «по данным» в ПВЗ появляется отрицательное число свободных мест;
- переполнение по данным никого не останавливает: машина с посылками уже в пути.

**Как проявляется:** машина с 8 посылками приезжает в ПВЗ, где мест нет; посылки остаются в машине и едут
на следующий день; клиент получает новый срок уже после оплаты; оператор ПВЗ вручную «распихивает» посылки.

**Симптомы:** `free_places < 0`; доля ПВЗ в состоянии `PAUSED` в момент прибытия машины; посылки, зависшие
на приёмке ПВЗ дольше суток.

### RC-6. Отмена заказа против сборки и передачи курьеру («фантомная посылка»)

**Участники:** клиент, оператор поддержки, WMS (сборка), delivery-orchestrator, курьер, ПВЗ/постамат.

**Раскадровка:**

```
T1  WMS: заказ #77 переведён ASSEMBLING (товар уже снят с полки)
T2  Клиент: «отменить» -> order-service: статус CANCELLED, инициирован возврат денег
T3  WMS (через 40 с): «собран» -> пишет ASSEMBLED поверх CANCELLED
T4  delivery-orchestrator: «передан курьеру» -> HANDED_TO_DELIVERY
T5  Курьер везёт заказ, за который клиенту уже вернули деньги
```

Тот же конфликт в других комбинациях:

- клиент отменяет уже переданный курьеру заказ → курьер приезжает, клиент отказывается, посылка уезжает
  назад, но в системе она числится «доставленной»;
- оператор отменяет заказ в поддержке, пока клиент отменяет его в приложении → две отмены, два возврата;
- заказ отменён, но резерв стока и место на полке не сняты → товар «занят» навсегда;
- заказ отменён в момент, когда посылка уже уложена в ячейку постамата → ячейку нужно освобождать, но
  никто не знает, что она занята этой отменой.

**Почему конфликт возможен:** отмена — это одна запись, а сборка, отгрузка, закладка идут независимыми
путями через очереди с задержкой в десятки секунд и минуты. Событие «отмена» и событие «собран» **не имеют
общего порядка** и не отменяют друг друга.

**Как проявляется:** клиент отменил заказ, но получил SMS «курьер в пути»; вернули деньги и одновременно
доставили товар; WMS собрал заказ, который уже отменён; посылка вернулась на склад и физически там лежит,
но в доступных остатках не числится.

**Симптомы:** статусы вида `CANCELLED → ASSEMBLED → HANDED_TO_DELIVERY` в истории заказа; заказы, у которых
есть и `refund`, и `delivered_at`; расхождение «отменено» в order-service и «отгружено» в WMS.

### RC-7. Отмена против оплаты, а также двойной возврат денег

**Участники:** клиент, payment-service, платёжный провайдер (вебхуки с ретраями), поддержка.

**Раскадровка A — оплата приходит после отмены:**

```
T1  Клиент: оплатить -> запрос в провайдер ушёл
T2  Клиент (не дождавшись): «отменить заказ» -> CANCELLED, попытка вернуть деньги
T3  Провайдер: вебхук «оплачено успешно» (через 3 секунды / через 3 часа / дважды)
T4  payment-service: помечает платёж оплаченным для CANCELLED-заказа
    -> деньги списаны, заказ отменён, возврата нет
```

**Раскадровка B — два возврата по одному платежу:**

```
T1  Клиент нажимает «отменить и вернуть» -> refund #1 в провайдер
T2  Запрос идёт 8 секунд, клиент решает, что не сработало, и пишет в поддержку
T3  Оператор делает возврат вручную -> refund #2
T4  Провайдер исполняет оба -> клиент получает деньги дважды
```

**Особенности этой гонки:**

- провайдер ретраит вебхуки часами и присылает дубликаты, причём заказ к этому моменту мог поменять
  статус несколько раз;
- возврат инициируется из трёх мест: клиент, поддержка, автоматический процесс при отмене/истечении срока;
- «оплата» и «отмена» идут в разные сервисы и не сериализуются: payment-service ничего не знает о том,
  что order-service уже отменил заказ;
- сумма к возврату зависит от собранности заказа (частичный возврат за отсутствующие позиции), и она
  считается по состоянию, которое уже устарело.

**Как проявляется:** «списали за отменённый заказ», «вернули дважды и требуют обратно», заказы-зомби
в статусе CANCELLED с успешным платежом, отрицательные балансы клиентов.

**Симптомы:** платежи в статусе `PAID` у заказов `CANCELLED`; `SUM(refunds) > order.total`; повторные
`payment_id` в вебхуках с одним и тем же `event_id`.

### RC-8. Двойное назначение курьера на один заказ

**Участники:** delivery-orchestrator (3 реплики), планировщик по расписанию (2 экземпляра), курьерская
служба партнёра, курьер.

**Раскадровка:**

```
T1  Оба экземпляра планировщика в 10:00:00 берут из очереди событие «заказ #12 требует курьера»
T2  Экземпляр #1: назначает курьера К-55, пишет assignment(A)
T3  Экземпляр #2: назначает курьера К-81, пишет assignment(B)   <-- оба назначения живы
T4  К-55 и К-81 оба получают наряд и оба едут
```

Причины: задача из очереди доставлена **at-least-once**, а обработчик не различает «это то же событие».
Плюс диспетчер может назначить вручную одновременно с автоматикой, а партнёрская служба — прислать своего
курьера вебхуком «наряд принят».

**Как проявляется:** два курьера у одной двери; в приложении мигает «курьер Иван», потом «курьер Пётр»;
бонус/комиссия начислены дважды; клиенту дважды звонят.

**Симптомы:** больше одного активного назначения на заказ; дубли `assignment.created` для одного
`order_id` в пределах секунд; двойные начисления в отчёте по курьерам.

### RC-9. Статусы доставки приходят не в том порядке и с дублями

**Участники:** транспортная компания / курьерская служба (вебхуки), delivery-orchestrator, order-service,
notification-service, программа лояльности.

**Раскадровка:**

```
T1  ТК: «вручено получателю» (вебхук пришёл первым из-за ретрая на их стороне)
T2  orchestrator: заказ -> DELIVERED, баллы начислены, отправлено «спасибо за покупку»
T3  ТК: «принято в сортировочном центре» (задержавшийся вебхук)
T4  обработчик «принято» переводит статус назад -> IN_TRANSIT
T5  ТК: «вручено» (дубликат) -> баллы начислены ещё раз
```

**Что именно ломается:** у событий партнёра нет монотонного признака «это состояние новее предыдущего»:
статус — просто строка, которая записывается поверх текущего значения. При переупорядочивании и дублях
статус может **регрессировать** и **повторно выполнять побочные эффекты** (начисление баллов, отправка SMS,
закрытие заказа, старт таймера возврата).

**Особые варианты:**

- посылка в ПВЗ: вебхук «выдано» от ПВЗ приходит раньше, чем «принято на полку»;
- постамат: устройство офлайн отправляет пачку событий за сутки сразу после восстановления связи;
- межгород: ТК меняет трек-номера, и события старого трека применяются к новому заказу.

**Как проявляется:** клиент видит «доставлено → в пути → доставлено»; заказ закрыт, потом снова открыт;
баллы начислены дважды; SMS «заберите заказ» приходит после того, как его уже забрали.

**Симптомы:** регресс `delivery_status` в истории; число переходов в `DELIVERED` больше одного на заказ;
дубли исходящих уведомлений по одному `order_id`.

### RC-10. Частичная отмена при разделении заказа на отправления

**Участники:** клиент, order-service, WMS, доставка (несколько отправлений по разным адресам/способам).

**Как устроено:** заказ из 5 позиций может разъехаться в 3 отправления: 2 позиции курьером сегодня,
2 позиции в ПВЗ, 1 позиция самовывозом из другого магазина. У каждого отправления свои резервы, свой
трек-номер, свой срок и своя стоимость доставки.

**Раскадровка:**

```
T1  Клиент: «отменить позицию №3» (она уже зарезервирована под отправление в ПВЗ)
T2  order-service: помечает позицию отменённой, пересчитывает итог заказа
T3  WMS (параллельно, не зная об отмене): собирает все 5 позиций по старому заданию
T4  Отправление в ПВЗ уезжает с отменённой позицией; сумма заказа уже меньше
```

**Что именно ломается:** «отмена позиции» и «сборка позиции» — это записи в разных сервисах без общего
порядка; итог заказа пересчитывается по одному состоянию, а отгрузка идёт по другому. Одновременно
возникает вопрос, какое из отправлений считать «тем самым», к которому относится возврат денег.

**Как проявляется:** клиенту вернули деньги за позицию и всё равно её привезли; отправление приезжает
в ПВЗ, но в системе заказ уже частично отменён и приёмка не проходит; сумма к оплате меняется после оплаты.

**Симптомы:** сумма позиций отправлений ≠ сумма заказа; отменённая позиция в составе отгруженного
отправления; расхождение возвратов по отправлениям и по заказу.

### RC-11. Вес и тариф изменились между расчётом стоимости и оплатой

**Участники:** клиент, delivery-tariff-service (кэш тарифов), WMS (фактическое взвешивание), payment-service.

**Раскадровка:**

```
T1  Клиент видит «доставка 290 ₽» (расчёт по весу 1 кг из карточки товара)
T2  Клиент оплачивает 290 ₽ + товар
T3  Склад взвешивает: фактический вес 3.2 кг (упаковка, комплект, объёмный вес)
T4  Тариф по факту — 690 ₽; тарифная сетка к этому моменту тоже обновилась (кэш отдал старую)
T5  Заказ нужно либо доставлять себе в убыток, либо просить доплату у клиента
```

**Что именно ломается:** стоимость доставки считается по данным, которые меняются **после** момента оплаты
(вес, зона, тариф, способ доставки). Проверка «цена верна» и фактическое исполнение разделены часами.
Кэш тарифов и кэш карточек товара живут отдельно, поэтому в момент оформления клиент, сервер и склад
могут видеть три разные цены.

**Как проявляется:** клиент получает «доплатите 400 ₽ или отменим»; заказ уходит в убыток; в чеке одна
сумма, в бухгалтерии другая; при смене способа доставки (курьер → ПВЗ) старая цена не пересчитывается.

**Симптомы:** расхождение `quoted_delivery_price` и `charged_delivery_price`; доля заказов с перевесом;
доля заказов, где способ доставки менялся после оплаты.

### RC-12. Ретрай на границе со службой доставки без идемпотентности

**Участники:** delivery-orchestrator, курьерская служба партнёра / ТК (HTTP API), WMS (печать накладных).

**Раскадровка:**

```
T1  orchestrator: POST /shipments {order: 42} -> партнёр создал накладную NR-1
T2  Ответ не дошёл (таймаут 30 с)
T3  orchestrator ретраит POST /shipments {order: 42} -> партнёр создал накладную NR-2
T4  У заказа 42 две накладные и два трек-номера; груз может поехать двумя посылками
```

Аналогично на других границах:

- печать накладной в WMS: двойной вызов → два документа, склад собирает по тому, который распечатался;
- SMS/push: два одинаковых уведомления «заказ в пути»;
- захват денег (capture) вызван дважды из-за ретрая — частичное двойное списание;
- сообщение в очередь отправлено дважды → два резерва, две задачи на маршрут.

**Почему это гонка, а не просто дубль:** два обработчика одного и того же запроса работают параллельно
(ретрай ушёл раньше, чем завершился первый), поэтому оба создают сущность, оба пишут в БД, и **порядок
их записей непредсказуем** — итоговое состояние зависит от того, чей ответ пришёл последним.

**Как проявляется:** у одного заказа две накладные; посылка «потерялась», потому что сканировали трек,
которого нет в системе; клиенту приходят дубли уведомлений; в отчёте по доставке заказ посчитан дважды.

**Симптомы:** `count(track_number) > 1` на заказ; совпадающие по составу `shipment` с разными id;
дубли `notification.sent` с одинаковым телом в пределах секунд.

### RC-13. Кэш статуса разошёлся с базой (клиент и поддержка видят разное)

**Участники:** order-service, Redis-кэш статусов, BFF/приложение клиента, интерфейс поддержки.

**Раскадровка:**

```
T1  order-service: заказ #90 -> CANCELLED (в БД)
T2  Инвалидация кэша не сработала / сработала на другой реплике / ключ протух позже
T3  Клиент читает карточку заказа -> из кэша -> «в пути»
T4  Поддержка читает из БД -> «отменён» и говорит клиенту «заказ отменён»
T5  WMS продолжает сборку, потому что читает ещё один кэш — статусов сборки
```

**Что именно ломается:** статус заказа — это **одни и те же данные в трёх-четырёх хранилищах** (БД, кэш
карточки, кэш списка заказов, кэш витрины), которые обновляются независимо, в разное время и на разных
репликах. Запись «отменён» может быть видна в одном месте и не видна в другом часами.

**Как проявляется:** клиент видит «в пути», поддержка — «отменён»; в списке заказов статус один,
в карточке другой; после обновления страницы статус «прыгает»; клиенту приходит операторское решение,
принятое по устаревшим данным.

**Симптомы:** расхождение кэша и БД при сверке; разное значение статуса для одного заказа в списке и в
карточке; жалобы «в приложении написано одно, оператор говорит другое».

### RC-14. ПВЗ закрылся или приостановил приём во время назначения заказа

**Участники:** клиент, pvz-service (справочник ПВЗ), планировщик межскладских перевозок, оператор ПВЗ.

**Раскадровка:**

```
T1  Клиент выбирает ПВЗ «Тверская-14» (по справочнику он активен)
T2  Оператор ПВЗ в этот момент ставит статус PAUSED (нет мест / ремонт / отпуск)
T3  order-service назначает заказ на «Тверская-14» по данным, прочитанным на шаге T1
T4  Машина едет в закрытый пункт; посылка разворачивается или лежит в машине
```

**Варианты:**

- ПВЗ закрылся насовсем, а заказы, уже назначенные на него, не переназначены;
- заказ переназначен на другой ПВЗ, но старое назначение не снято → в двух пунктах ждут одну посылку;
- после переназначения клиент получил SMS со старым адресом (уведомление ушло раньше изменения);
- лимит ПВЗ уменьшился (часть полок закрыли), и все ранее занятые места стали «лишними».

**Как проявляется:** клиент приезжает в ПВЗ, а его посылки там нет; посылка висит в пути неделю; два ПВЗ
одновременно «ждут» один заказ.

**Симптомы:** назначения на ПВЗ со статусом `PAUSED`/`CLOSED`; заказы без активного назначения после
переназначения; SMS с адресом, отличным от финального назначения.

### RC-15. Двойная обработка или потеря задачи планировщика

**Участники:** планировщик (cron + очередь), воркеры (N реплик), order-service, pvz-service, locker-service.

**Типичные задачи:** «истёк срок хранения в ПВЗ → вернуть», «истёк срок в постамате → забрать курьером»,
«заказ не забран → автозакрытие», «пересчитать маршрут», «списать плату за хранение сверх срока».

**Раскадровка A — двойное срабатывание:**

```
T1  Cron в 03:00 ставит задачу TASK-1 «срок хранения истёк, заказ #500»
T2  Два воркера одновременно берут TASK-1 (at-least-once, видимость сообщения не истекла)
T3  Воркер #1: списывает плату за хранение, инициирует возврат, освобождает место
T4  Воркер #2: списывает плату за хранение ещё раз, снова освобождает место
    -> двойное списание, «минус одно» свободное место на полке
```

**Раскадровка B — потеря задачи:**

```
T1  Воркер взял задачу и упал (деплой / OOM) до подтверждения
T2  Сообщение потеряно (нет повторной доставки) -> посылка навсегда «лежит» в ПВЗ сверх срока
```

**Почему это гонка:** одна и та же операция «срок истёк» может быть выполнена дважды или ни разу;
исполнение не связано с фактическим состоянием (посылка уже выдана, а задача всё ещё жива; посылка ещё
лежит, а таймер уже отработал). Кроме того, таймер и ручное действие оператора («выдать вручную»)
конкурируют за один и тот же заказ.

**Как проявляется:** с клиента списали плату за хранение дважды; посылка «зависла» в ПВЗ на месяцы;
место на полке освободилось, а посылка физически там; возврат инициирован для уже выданного заказа.

**Симптомы:** более одного `storage_fee` на заказ; заказы, чей срок хранения истёк, но нет события
возврата; расхождение «физически в ПВЗ» и «по данным выдано».

### RC-16. Клиент меняет адрес или слот во время назначения курьера

**Участники:** клиент, order-service, slot-service, delivery-orchestrator, курьерское приложение.

**Раскадровка:**

```
T1  Заказ #33: адрес «Ленина 5», слот 18:00–20:00
T2  Клиент: меняет адрес на «Мира 40» (другая зона) и слот на 14:00–16:00
T3  orchestrator (параллельно): назначает курьера по старому адресу и старому слоту
T4  Клиентская запись обновилась, но наряд курьера уже сформирован по старым данным
    -> курьер едет на «Ленина 5», заказ не доставлен
```

**Что именно ломается:** адрес и слот — это данные, которые читаются в момент назначения и записываются
в наряд, но клиент может менять их в любой момент до передачи. Изменение и назначение — две независимые
записи в разных сервисах, между ними нет «версии» заказа, с которой можно сверить актуальность наряда.
Отдельно: смена слота должна освободить старый слот и занять новый — и это тоже две операции, между
которыми ёмкость обоих слотов искажена.

**Как проявляется:** курьер приезжает не туда; заказ считается «доставленным» по старому адресу; в старом
слоте остаётся «призрачный» занятый слот, а в новом может не хватить места.

**Симптомы:** адрес в наряде ≠ адрес в заказе; «занятость» слота, на который нет ни одного заказа;
жалобы «курьер приехал по старому адресу».

### RC-17. Генерация номеров заказов и трек-номеров на нескольких инстансах

**Участники:** order-service (N реплик), delivery-orchestrator, WMS.

**Раскадровка:**

```
T1  instance #1: читает последний номер заказа -> 104999, формирует 105000
T2  instance #2: читает тот же последний номер -> 104999, формирует 105000
T3  оба вставляют 105000 -> либо конфликт, либо (если ограничения нет) два заказа с одним номером
```

Аналогично для трек-номеров и номеров накладных, которые генерируются локально, до отправки партнёру.
Отдельный случай — разрыв нумерации при откате транзакции: номер «сгорел», и в отчётности появляются дыры,
которые потом ищут как потерянные заказы.

**Как проявляется:** клиент и поддержка не могут однозначно назвать заказ («у меня заказ 105000» — их два);
трек-номер в системе не находится у перевозчика; в бухгалтерии дубли.

**Симптомы:** дубли номеров заказов/треков; расхождение нумерации и фактического числа заказов;
ручные склейки заказов в поддержке.

## 6. Почему именно эта система особенно подвержена гонкам

1. **Много независимых источников истины.** Статус заказа живёт в order-service, статус доставки — в
   orchestrator и у партнёров, остаток — в inventory и WMS, место на полке — в pvz-service, ячейка — в
   locker-service и в самом устройстве. Между ними нет единого порядка событий.
2. **Все границы «at-least-once».** Очереди, вебхуки провайдера и партнёров, ретраи на шлюзах. Любая
   операция может быть выполнена дважды, и почти каждая — в обратном порядке.
3. **Нет распределённых транзакций.** Локальные транзакции + саги/компенсации, которые выполняются
   секунды и минуты; всё это время система находится в промежуточном, «полу-применённом» состоянии.
4. **Физический мир не откатывается.** Резервы можно отменить, но посылку, уже уложенную в ячейку,
   отправленную машину и приехавшего курьера отменить нельзя. Ошибка превращается в физическое действие.
5. **Дискретные ёмкости.** Слот, полка, ячейка — целые числа. «Почти хватило» не существует, а спрос в
   пик кратно превышает ёмкость.
6. **Кэши в горячем пути.** Остатки, статусы, тарифы, занятость ячеек читаются из кэша, который обновляется
   отдельно от источника.
7. **Люди в тех же данных.** Оператор поддержки, диспетчер и оператор ПВЗ действуют руками параллельно
   с автоматикой, не всегда через тот же API, и не видят, что «прямо сейчас» делает процесс.
8. **Часовые сдвиги.** Разница во времени между серверами, устройствами постаматов и партнёрами приводит
   к тому, что «одинаковые» события получают разные отметки времени и сравниваются неверно.
9. **Пики.** В 18:00–22:00 нагрузка в 5–8 раз выше средней; на пике вероятности гонок умножаются,
   а таймауты и ретраи учащаются — именно тогда и появляются все описанные выше инциденты.

## 7. Как гонки суммируются: классы инцидентов

| Класс | Из каких гонок складывается | Что видит бизнес |
|---|---|---|
| Продали больше, чем есть | RC-1, RC-2, RC-10 | отмены после оплаты, отрицательные остатки, штрафы маркетплейса |
| Взяли деньги дважды / вернули дважды | RC-2, RC-7, RC-15 | возвраты, чарджбэки, претензии, ручные сверки |
| Переполнили ёмкость | RC-3, RC-4, RC-5, RC-14 | переносы сроков, отказы ПВЗ, сломанные постаматы |
| Сделали лишнюю физическую работу | RC-6, RC-8, RC-12 | две посылки, два курьера, лишние накладные, убыток |
| Данные разошлись между системами | RC-9, RC-13, RC-17 | «в приложении одно, у оператора другое», ручные склейки |
| Стоимость посчитана неверно | RC-11, RC-10 | доплаты, убыточные доставки, споры по чекам |
| Задача не выполнена вовсе | RC-15, RC-4 | посылки-«зомби», вечно занятые места, зависшие заказы |

Общая закономерность: **каждая гонка в отдельности редкая (доли процента), но при 120 000 заказов в сутки
это десятки-сотни инцидентов в день**, и почти каждый требует ручного разбора: физическая посылка уже
где-то едет, а данные в четырёх системах говорят разное.

## 8. Глоссарий классов гонок из этого документа

| Класс | Суть |
|---|---|
| **Check-then-act (TOCTOU)** | проверка условия и действие по результату разделены; между ними состояние меняется |
| **Lost update** | два потока читают одно значение и оба пишут поверх друг друга; чья-то запись теряется |
| **Write skew** | каждый поток по отдельности действует по правилам, но вместе они нарушают инвариант |
| **Double submission** | один и тот же запрос исполняется дважды (клик, ретрай, дубль вебхука) |
| **Non-idempotent retry** | повтор операции создаёт новую сущность вместо возврата результата первой попытки |
| **Out-of-order events** | события одного объекта приходят не в том порядке, в котором произошли |
| **Stale cache / read-your-writes** | чтение возвращает устаревшее значение, хотя запись уже сделана |
| **At-least-once delivery** | сообщение гарантированно доставлено, но может быть доставлено несколько раз |
| **Lost task** | задача взята в работу и потеряна при сбое обработчика — не выполнена ни разу |
| **ABA** | значение изменилось и вернулось к прежнему, и проверка «не изменилось ли» ошибочно проходит |

## 9. Что этот документ намеренно не содержит

- вариантов решения, подходов и паттернов (даже в виде намёков «а надо было бы…»);
- выбора хранилищ, схем данных и протоколов;
- оценки, какие из гонок «главные» и в каком порядке их закрывать.

Документ фиксирует **только проблему и полный список гонок в ней** — как материал для отдельного разбора
решений.

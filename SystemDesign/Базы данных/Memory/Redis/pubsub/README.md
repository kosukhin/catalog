# Redis Pub/Sub — чат

Рабочий пример использования **Redis Pub/Sub** на реальном приложении — многопользовательский
чат (Node.js + Express + WebSocket + ioredis в Docker).

- [Приложение](./app/) — сервер чата, CLI-клиент, веб-интерфейс
- Тесты — [app/test/pubsub.test.js](./app/test/pubsub.test.js)

## Что такое Pub/Sub

**Publish/Subscribe** — модель обмена сообщениями «издатель → подписчики». Отправитель (publisher)
не знает, кто получит сообщение: он публикует его в **канал** (channel), а Redis рассылает его всем
клиентам, подписанным (SUBSCRIBE) на этот канал в данный момент.

```bash
# 1. Подписчик: слушаем канал "chat:general"
#    Терминал блокируется и начинает получать сообщения в реальном времени
SUBSCRIBE chat:general

# 2. Издатель: публикуем сообщение в канал
#    Возвращает ЧИСЛО ПОЛУЧАТЕЛЕЙ — сколько клиентов получили сообщение
PUBLISH chat:general '{"user":"alice","text":"привет"}'
# → 3        (сообщение доставлено трём подписчикам)

# 3. Отписаться от канала
UNSUBSCRIBE chat:general
```

Ключевые свойства Pub/Sub:

- **Fire-and-forget** — сообщение не сохраняется: если подписчика нет в момент PUBLISH, он его
  **не получит никогда**. Нет ни очередей, ни подтверждений, ни повторной доставки.
- **Мгновенность** — доставка в реальном времени, накладные расходы минимальны.
- **Шина между сервисами** — классический способ разнести события между инстансами приложения
  (см. ниже: два контейнера app обмениваются сообщениями через один Redis).

### Pub/Sub vs Streams (см. соседний пример `../stream/`)

| | Pub/Sub | Streams |
|---|---|---|
| Доставка | только онлайн-подписчикам, в момент публикации | persistent-журнал, история читается позже |
| Гарантии | нет (at most once, с потерями) | XACK + XAUTOCLAIM (at least once) |
| Группы потребителей | нет | consumer groups, разделение нагрузки |
| Хранение | нет | до MAXLEN/XTRIM |

Pub/Sub выбирают там, где нужна **реалтайм-рассылка** и потеря сообщения при недоступности
получателя допустима: чаты, уведомления, метрики, инвалидация кешей, fan-out событий.

## Архитектура примера

```
  CLI-клиент ──ws──►  app1 :3002 ──SUBSCRIBE chat:general──┐
  браузер   ──ws──►  app1 :3002 ──PUBLISH──────────────────┼──► Redis :6381
  браузер   ──ws──►  app2 :3003 ──SUBSCRIBE chat:general──┘        │
                                                                   ▼
                                     Redis рассылает сообщение всем подписчикам канала
                                     → каждый инстанс пересылает его своим WS-клиентам
```

Компоненты:

| Файл | Роль |
|---|---|
| [src/pubsub.js](./app/src/pubsub.js) | Ядро: два соединения ioredis — `redis` (PUBLISH, история) и `subscriber` (SUBSCRIBE). ioredis в режиме подписки не может выполнять обычные команды, поэтому соединений два. |
| [src/server.js](./app/src/server.js) | HTTP + WebSocket. Подписка на канал `chat:<room>` создаётся, когда в комнату входит первый клиент процесса, и снимается, когда уходит последний. |
| [src/app.js](./app/src/app.js) | REST API (`/rooms/:room/history`, `/stats`, `POST /rooms/:room/messages`) и веб-клиент на `GET /`. |
| [src/client.js](./app/src/client.js) | CLI-чат-клиент в терминале. |

**Поток сообщения:**

1. Клиент открывает `WS /ws?room=general` и отправляет `{ user, text }`.
2. Сервер вызывает `PUBLISH chat:general '{"user":"alice","text":"..."}'` — Redis возвращает
   число получателей (сколько процессов подписаны на канал).
3. Redis доставляет JSON всем подписанным процессам (в том числе app2 — пользователь там
   видит сообщение так же мгновенно, как и пользователь на app1).
4. Каждый процесс рассылает сообщение своим WebSocket-клиентам этой комнаты.

**История сообщений:** Pub/Sub ничего не хранит, поэтому история — отдельный механизм:
`LPUSH chat:<room>:history + LTRIM 0 99 + EXPIRE 3600` (последние 100 сообщений, час жизни).
При подключении нового клиента сервер отправляет ему историю из этого списка. Это наглядно
показывает границу ответственности: Pub/Sub — только живая доставка, хранение делается отдельно
(в реальном продукте вместо этого часто берут Redis Streams или очередь).

## Как запустить

```bash
cd app
docker compose up -d --build

# Веб-клиент (откройте в двух окнах браузера — один на 3002, второй на 3003,
# и увидите горизонтальное масштабирование в действии)
open http://localhost:3002/
open http://localhost:3003/

# Два CLI-клиента в терминале (пишите текст + Enter)
node src/client.js alice general 3002
node src/client.js bob   general 3003

# История комнаты
curl http://localhost:3002/rooms/general/history

# Отправить сообщение через REST (PUBLISH)
curl -X POST http://localhost:3002/rooms/general/messages \
  -H 'Content-Type: application/json' -d '{"user":"rest","text":"привет из curl"}'

# Активные каналы и число подписчиков
curl http://localhost:3002/stats

# Подглядеть Pub/Sub глазами Redis
docker compose exec redis redis-cli PUBSUB CHANNELS "chat:*"
docker compose exec redis redis-cli SUBSCRIBE chat:general
```

## Тесты

```bash
cd app
docker compose up -d redis
npm test
```

Тесты проверяют: доставку сообщения подписчикам, счётчик `receivers`
(в т.ч. `receivers = 0` без подписчиков — сообщение потеряно), сохранение истории
и содержимое `PUBSUB CHANNELS / NUMSUB`.

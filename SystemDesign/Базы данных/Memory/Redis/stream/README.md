# Redis Streams

Рабочий пример использования **Redis Streams** — лога сообщений с consumer groups.

- [Приложение](./app/) — Node.js + Express + Redis Streams в Docker
- Тесты — [app/test/streams.test.js](./app/test/streams.test.js)

## Что такое Streams

Stream — это **append-only лог** (журнал) внутри Redis. Представьте бесконечный файл, в который
можно только дописывать записи в конец: producer пишет события, consumers читают их в том же порядке.

Каждая запись имеет:
- **ID** вида `timestamp-seq` (например `1719000000000-1`) — генерируется Redis автоматически, задаёт порядок;
- **поля** (как в хеше): `"user" → "alice", "action" → "login"`.

Главное отличие от обычного Pub/Sub: записи **сохраняются** в Redis, пока их не обрезать. Потребитель,
пришедший через час, прочитает все сообщения с начала — Pub/Sub отдал бы их только тем, кто слушал в момент публикации.

### Базовые команды — что делает каждая

```bash
# 1. PRODUCER: добавить запись в стрим "events"
#    "*" = ID сгенерируй сам (timestamp-seq), дальше — пары поле-значение
XADD events * user "alice" action "login"
# → 1719000000000-1   (Redis вернул ID новой записи)

# 2. Создать consumer group "workers" для стрима "events"
#    "0" = с какого ID группе начинать читать (0 = вся история, "$" = только новые)
#    Достаточно выполнить один раз — группа создаётся и запоминает позицию чтения
XGROUP CREATE events workers 0

# 3. CONSUMER: воркер с именем "c1" из группы "workers" просит новые сообщения
#    COUNT 10  — максимум 10 за раз
#    BLOCK 5000 — ждать новых до 5 секунд, вместо мгновенного пустого ответа
#    ">"       — давать только НОВЫЕ сообщения, которые ещё никто из группы не забрал
XREADGROUP GROUP workers c1 COUNT 10 BLOCK 5000 STREAMS events ">"

# 4. Подтвердить обработку: сообщение с этим ID считается успешно обработанным
#    Без XACK сообщение остаётся "pending" — Redis будет считать, что его ещё никто не обработал
XACK events workers 1719000000000-1
```

Итого сценарий в 4 шага: **пишем** (`XADD`) → **один раз создаём группу** (`XGROUP CREATE`) →
**воркеры читают** (`XREADGROUP`) → **после успешной обработки подтверждают** (`XACK`).

Для полноты, ещё три команды, которые используются в демо:

```bash
# Сколько записей сейчас в стриме
XLEN events

# Информация о стриме: первый/последний ID, consumer groups и их позиции
XINFO STREAM events

# Какие сообщения забраны, но не ACKнуты (PEL): кто держит, сколько ждёт
XPENDING events workers
```

Ключевые возможности по сравнению с Pub/Sub:

| | Pub/Sub | Streams |
|---|---|---|
| Доставка | fire-and-forget, только онлайн-подписчикам | persistent, новые потребители читают историю |
| Гарантии | нет подтверждений | XACK + XAUTOCLAIM (re-delivery) |
| Группы | нет | consumer groups, нагрузка делится между воркерами |
| Хранение | нет | до MAXLEN/XTRIM |

## Delivery guarantees: at most once vs at least once

Какая гарантия доставки у вашей системы — определяется тем, **когда вы ACK-аете сообщение**:

### At most once (не более одного раза)

ACK **до** обработки: сообщение считается доставленным сразу после чтения.

```
XREADGROUP ...          // забрали сообщение
XACK                    // сразу подтвердили
обработка...            // если процесс упал здесь — сообщение потеряно
```

- ✅ Нет дубликатов.
- ❌ Можно потерять сообщение при падении между XACK и завершением обработки.
- Когда подходит: метрики, счётчики, телеметрия — где потеря одного события не критична.

### At least once (не менее одного раза) — используется в этом примере

ACK **после** успешной обработки: упавшее сообщение остаётся в PEL и доставляется повторно.

```
XREADGROUP ...          // забрали сообщение
обработка...            // если процесс упал здесь — сообщение не ACKнуто
XACK                    // подтвердили только после успеха
// позже: XAUTOCLAIM подхватывает не-ACKнутые сообщения из PEL
```

- ✅ Сообщения не теряются: `XAUTOCLAIM` возвращает зависшие из PEL другому воркеру.
- ❌ Возможны **дубликаты**: воркер мог обработать сообщение, но упасть до XACK — при повторной доставке оно обработается ещё раз. Обработчик должен быть **идемпотентным** (например, дедупликация по ID сообщения: `SET processed:{id} NX EX ttl`).
- Когда подходит: платежи, заказы, уведомления — где потеря недопустима.

### Сравнение

| | At most once | At least once |
|---|---|---|
| ACK момент | до обработки | после обработки |
| Потеря сообщений | возможна | исключена |
| Дубликаты | исключены | возможны → нужна идемпотентность |
| Механизм | XACK сразу после XREADGROUP | XACK после обработки + XAUTOCLAIM из PEL |

> **Exactly once** в чистом виде Redis не даёт — его добирают идемпотентностью потребителя поверх at-least-once.

В демо: воркер не ACK-ает сообщение `action:"crash"` (имитация падения), а таймер с `XAUTOCLAIM` восстанавливает его из PEL — это и есть at-least-once в действии.

## Consumer Group — как работает

- Каждое сообщение имеет ID `timestamp-seq` (например `1719000000000-1`).
- Группа хранит `last-delivered-id` — новое сообщение доставляется каждому воркеру ровно один раз (round-robin).
- Неподтверждённые (XACK не пришёл) сообщения попадают в **PEL** (pending entries list) — их можно забрать
  другим воркером через `XAUTOCLAIM` (нужен минимум idle-time). Это и есть «at-least-once» доставка.

В примере: воркер обрабатывает сообщение и **крэшится** на сообщении `"crash"`,
затем второй воркер через `XAUTOCLAIM` подхватывает его из PEL.

## Как запустить

```bash
cd app
docker compose up -d --build

# создать заказ
curl -X POST http://localhost:3001/orders -H 'Content-Type: application/json' \
  -d '{"userId":"alice","total":5000,"items":["book","pen"]}'

# проверить статус заказа (какие группы обработали)
curl http://localhost:3001/orders/<orderId>

# посмотреть статистику: длина стрима, pending по каждой группе
curl http://localhost:3001/stats

# дашборд
open http://localhost:3001/
```

## Архитектура примера

**Стрим:** `orders` (append-only журнал заказов, `MAXLEN ~ 1000`)

**3 независимые consumer groups** — каждая читает одни и те же записи, но имеет свой `last-delivered-id` и свою PEL:

| Группа | Обработчик | Что делает |
|--------|------------|------------|
| `inventory` | `handleInventory` | Резервирует товар на складе (50ms) |
| `payment` | `handlePayment` | Списывает деньги (30ms). Имитация падения при userId: crash |
| `email` | `handleEmail` | Отправляет подтверждение (20ms) |

**Как это работает:**

1. `POST /orders` - XADD orders * orderId ... userId ... total ... items ... - заказ попадает в стрим.
2. Три воркера (XREADGROUP GROUP group consumer ... STREAMS orders >) параллельно читают новые заказы.
3. После успешной обработки воркер вызывает XACK orders group id и записывает status:group: done в хеш order:orderId.
4. Если обработчик падает (сообщение не ACK-нуто) - заказ остаётся в PEL группы. Таймер каждые 2 сек вызывает XAUTOCLAIM для восстановления зависших сообщений.
5. `GET /orders/:id` - возвращает хеш заказа со статусами по каждой группе.
6. `GET /stats` - XLEN + XPENDING по каждой из 3 групп - JSON.

**Ключевая идея:** сообщение не извлекается из стрима при прочтении - оно остаётся там. Каждая consumer group - это закладка поверх журнала. Один заказ обрабатывается тремя независимыми сервисами, и каждый отслеживает свой прогресс отдельно.

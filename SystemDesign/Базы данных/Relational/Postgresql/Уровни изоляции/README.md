# Уровни изоляции в PostgreSQL

Каталог с теорией и рабочим примером: **два агента одновременно зачисляют и списывают деньги с общего счёта**, и при недостаточной изоляции транзакций баланс в поле таблицы становится неверным.

- [Теория и разбор (README)](./README.md) — этот файл
- [Рабочий пример](./) — PostgreSQL 16 в Docker + симуляция на [`agents-world`](../../../../../Инструменты/Для%20разработки/Симуляции/AgentsWorld/README.md)
- [Неповторяющееся чтение](./scripts/nonRepeatableRead.ts) — отдельный опыт на двух сессиях
- Тесты — [test/isolation.test.ts](./test/isolation.test.ts)

Проверено на PostgreSQL 16.2 (в `docker-compose.yml` — `postgres:16-alpine`).

---

## Что происходит в примере

У Анны и Петра **общий счёт на 1000 ₽**. Оба пользуются банком одновременно:

| Агент | Что делает | Сумма |
|---|---|---|
| `BankAgent-1` | зачисление зарплаты | `+500` |
| `BankAgent-2` | списание за аренду | `−300` |

Правильный итог всегда один: `1000 + 500 − 300 = 1200 ₽`. Но если приложение работает по привычной схеме «прочитать баланс → изменить в коде → записать новое число», а транзакция запущена на `READ COMMITTED`, то оба агента читают **1000**, каждый считает своё и записывает результат целиком. Второй `UPDATE` затирает первый:

```
BankAgent-1: 1000 + 500 = 1500  → UPDATE accounts SET balance = 1500
BankAgent-2: 1000 − 300 =  700  → UPDATE accounts SET balance =  700   ← «выиграл»
итог в БД: 700 ₽ вместо 1200 ₽, 500 ₽ просто исчезли
```

Обе транзакции при этом **успешны**: ни ошибок, ни предупреждений. Это и есть потерянное обновление (lost update).

## Быстрый старт

```bash
cd "SystemDesign/Базы данных/Relational/Postgresql/Уровни изоляции"

npm install        # pg + типы (agents-world линкуется из репозитория, см. package.json)
npm run db:up      # postgres:16-alpine на localhost:5433, схема и данные — из sql/

npm start          # прогон четырёх сценариев: 700 / 1200 / 1200 / 1200 ₽
npm test           # те же проверки через node --test
npm run levels     # неповторяющееся чтение: два SELECT внутри одной транзакции

npm run db:down    # остановить и удалить данные тома
npm run db:reset   # пересоздать базу с нуля (заново накатит sql/)
```

Порт на хосте — **5433**, чтобы не конфликтовать с локальным PostgreSQL на 5432. Настройки подключения лежат в [.env](./.env): `DATABASE_URL=postgres://bank:bank@localhost:5433/bank`.

Требуется Node.js 22.18+ (TypeScript исполняется напрямую, сборка не нужна).

## Схема данных

[`sql/01_schema.sql`](./sql/01_schema.sql):

| Таблица | Назначение |
|---|---|
| `users` | пользователи банка (Анна, Пётр) |
| `accounts` | счета; **баланс — просто целое число в поле `balance`** |
| `account_members` | кто владеет счётом; у общего счёта несколько владельцев |
| `operations` | журнал проводок: кто, что, сколько, что прочитал и что записал |

Триггеров и хранимых процедур нет намеренно: вся «логика перевода» — в приложении, поэтому корректность итога целиком зависит от уровня изоляции и от того, как именно приложение пишет баланс.

## Уровни изоляции в PostgreSQL

| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы | Потерянное обновление | Что делает PostgreSQL |
|---|---|---|---|---|---|
| `READ UNCOMMITTED` | невозможно | — | — | — | приравнен к `READ COMMITTED`: грязное чтение не разрешается никогда |
| `READ COMMITTED` (по умолчанию) | нет | **возможно** | **возможны** | **возможно** | каждая команда видит снимок, зафиксированный **до её начала** |
| `REPEATABLE READ` | нет | нет | нет | нет | снимок берётся один раз на всю транзакцию (snapshot isolation); конфликт записи — ошибка `40001` |
| `SERIALIZABLE` | нет | нет | нет | нет | `REPEATABLE READ` + SSI: отслеживаются опасные зависимости чтения/записи, `40001` чаще |

Что важно понимать про PostgreSQL:

1. **Уровень по умолчанию — `READ COMMITTED`.** Именно поэтому «прочитал → записал» в прикладном коде теряет данные без единой ошибки.
2. **`REPEATABLE READ` — это не «блокировки на чтение», а снимок.** Читать можно свободно, но попытка изменить строку, которую уже изменил кто-то другой, отменяет транзакцию: `ERROR: could not serialize access due to concurrent update` (код `40001`).
3. **`40001` — это не сбой, а приглашение повторить.** Транзакцию нужно целиком перезапустить; повтор обязателен, иначе приложение начнёт «падать» под нагрузкой.
4. **`SERIALIZABLE` не отменяет повторы**, а делает их чаще: SSI может отменить транзакцию, даже если строки не пересекались (write skew).
5. **`SELECT … FOR UPDATE` работает на любом уровне** и не требует повторов: строка блокируется до `COMMIT`, второй агент ждёт и читает уже новое значение.

## Механика потерянного обновления

Сценарий 1 (`read-modify-write`, `READ COMMITTED`), по шагам:

| Момент | BankAgent-1 (зачисление) | BankAgent-2 (списание) | `accounts.balance` |
|---|---|---|---|
| 1 | `BEGIN` | `BEGIN` | 1000 |
| 2 | `SELECT balance` → 1000 | `SELECT balance` → 1000 | 1000 |
| 3 | *барьер: ждём друг друга* | *барьер: ждём друг друга* | 1000 |
| 4 | `UPDATE … SET balance = 1500` | | 1500 (не зафиксировано) |
| 5 | `COMMIT` | | **1500** |
| 6 | | `UPDATE … SET balance = 700` | 700 |
| 7 | | `COMMIT` | **700** ❌ |

Обратите внимание на строку 6: `BankAgent-2` пишет `1000 − 300 = 700`, хотя в базе уже лежит 1500. `UPDATE` на `READ COMMITTED` не сверяет версию строки с той, что была прочитана, — он просто перезаписывает значение.

На `REPEATABLE READ` шаг 6 выглядит иначе:

| Момент | BankAgent-1 | BankAgent-2 | `accounts.balance` |
|---|---|---|---|
| 6 | | `UPDATE …` → **`ERROR 40001`** | 1500 |
| 7 | | `ROLLBACK`, затем новая транзакция: `SELECT` → 1500 | 1500 |
| 8 | | `UPDATE … SET balance = 1200`, `COMMIT` | **1200** ✅ |

## Как это устроено в коде

```
БД: users / accounts / account_members / operations   ← docker-compose + sql/
        ↑ два независимых соединения (по одному на поток)
agents/bankAgent.ts   агент agents-world: в start() проводит свою операцию
        ↑
src/world.ts          мир из двух агентов, threadPoolSize: 2
src/runner.ts         сценарий: сброс счёта → прогон мира → чтение итога и журнала
src/strategies.ts     три способа записи баланса (read-modify-write / for-update / atomic)
src/transfer.ts       повторы по 40001
src/report.ts         печать таблиц и сводки
scripts/simulate.ts   точка входа: четыре сценария подряд
```

Несколько решений, без которых пример был бы нечестным:

- **Параллелизм настоящий.** Два агента живут в двух потоках ОС (`worker_threads` пула `agents-world`), у каждого свой пул соединений `pg`. Это видно в отчёте: номера потоков у агентов разные (1, 2, 3, 4, …).
- **Барьер `FileBarrier`.** Без него гонка воспроизводилась бы через раз: один агент успевал бы зафиксировать транзакцию до чтения второго. Барьер (файлы-маркеры в `/tmp`, потому что память у потоков своя) гарантирует, что **оба уже прочитали баланс**, и только потом разрешает запись — как в реальном приложении, где между чтением и записью выполняется бизнес-логика.
- **Пауза «бизнес-логики»** (`logicDelayMs`: у списания 120 мс) делает порядок записей предсказуемым, поэтому итог первого сценария не «плавает»: всегда 700 ₽.
- **Результаты забираются штатным протоколом** `agents-world`: у каждого агента спрашивают состояние сообщением `status-request`, агент отвечает тем, что вернул его `describe()`.


## Что печатает `npm start`

Сценарий 1 — деньги потеряны молча (сокращённо):

```
Сценарий 1/4: Потерянное обновление
счёт: «Общий счёт Анны и Петра» · баланс на старте: 1000 ₽
стратегия: read-modify-write · уровень изоляции: READ COMMITTED

агент        поток  прочитал  записал  попыток  статус
BankAgent-1  1      1000      1500     1        зафиксировано
BankAgent-2  2      1000      700      1        зафиксировано

журнал проводок:
№   агент        вид         сумма   было   стало  изоляция
1   BankAgent-1  зачисление  +500    1000   1500   read committed
2   BankAgent-2  списание    −300    1000   700    read committed

итог в БД: 700 ₽ · ожидалось: 1200 ₽ · ❌ потеряно 500 ₽
```

Сценарий 2 — тот же код, но на `REPEATABLE READ`: PostgreSQL замечает конфликт, транзакция повторяется:

```
Сценарий 2/4: REPEATABLE READ и повтор транзакции
стратегия: read-modify-write · уровень изоляции: REPEATABLE READ

агент        поток  прочитал  записал  попыток  статус
BankAgent-1  3      1000      1500     1        зафиксировано
BankAgent-2  4      1500      1200     2        зафиксировано

отменённые попытки:
  BankAgent-2: попытка 1: 40001 — could not serialize access due to concurrent update

итог в БД: 1200 ₽ · ожидалось: 1200 ₽ · ✅ совпало
```

Сводка по всем четырём сценариям:

```
сценарий           изоляция          итог    ожидалось  вердикт
lost-update        READ COMMITTED    700 ₽   1200 ₽     ❌ ошибка
repeatable-read    REPEATABLE READ   1200 ₽  1200 ₽     ✅ верно
for-update         READ COMMITTED    1200 ₽  1200 ₽     ✅ верно
atomic             READ COMMITTED    1200 ₽  1200 ₽     ✅ верно
```

## Три способа не терять обновления

| Способ | Как выглядит | Цена | Когда выбирать |
|---|---|---|---|
| Уровень изоляции + повтор | `BEGIN ISOLATION LEVEL REPEATABLE READ` и повтор всей транзакции по `40001` | транзакции отменяются, нужен цикл повторов; нельзя держать транзакцию открытой долго | когда в транзакции несколько строк и нужно «всё или ничего» |
| Блокировка строки | `SELECT … FOR UPDATE` в начале транзакции | второй агент ждёт `COMMIT`; при разном порядке строк — дедлоки (`40P01`) | когда операция короткая и заранее известно, какие строки меняются |
| Атомарная команда | `UPDATE … SET balance = balance + $1 WHERE id = $2` | нельзя «посмотреть и решить» — но проверку можно вписать в `WHERE` | денежные приращения: счётчики, балансы, остатки |

Для денег обычно берут третий способ и добавляют проверку прямо в условие, чтобы списание не ушло в минус:

```sql
UPDATE accounts
   SET balance = balance - $2
 WHERE id = $1 AND balance >= $2
RETURNING balance;   -- нет строки → денег не хватило, откатываем транзакцию
```

## Неповторяющееся чтение: `npm run levels`

Отдельный опыт без агентов — две независимые сессии на одном счёте:

```
READ COMMITTED   первое чтение: 1000 ₽ · второе чтение: 1500 ₽ · значение изменилось (+500 ₽ от чужого COMMIT)
REPEATABLE READ  первое чтение: 1000 ₽ · второе чтение: 1000 ₽ · значение повторилось (снимок держится)
```

Внутри одной транзакции на `READ COMMITTED` два одинаковых `SELECT` могут вернуть разные числа: каждая команда берёт свой снимок. `REPEATABLE READ` держит один снимок на всю транзакцию — и именно поэтому при попытке записи в такой снимок PostgreSQL отвечает `40001`.

## Грабли

| Граблю | Что делать |
|---|---|
| `40001` на `REPEATABLE READ`/`SERIALIZABLE` | обернуть транзакцию в цикл повторов с небольшой паузой; без этого приложение падает под нагрузкой |
| `READ COMMITTED` (по умолчанию) | помнить, что он не защищает от потерянного обновления: его защищает блокировка или атомарный `UPDATE` |
| Второе чтение внутри транзакции | на `READ COMMITTED` оно вернёт уже другие данные; если нужна согласованность — `REPEATABLE READ` |
| `SELECT … FOR UPDATE` в разном порядке | два агента, блокирующие строки в разном порядке, получают дедлок `40P01` — тоже повод для повтора |
| Долгая транзакция | держит блокировки и мешает `VACUUM`: бизнес-логику (внешние вызовы) внутрь транзакции не тащить |
| `pg` и `bigint` | `pg` отдаёт `bigint` строкой, `integer` — числом; в реальных балансах берут `numeric`/`bigint` и `pg-types`, а не «просто число» |
| Повтор операции | у зачисления и списания должен быть идемпотентный ключ, иначе повтор транзакции рискует задвоить операцию |
| Журнал проводок | журнал в одной транзакции с балансом — единственный способ потом понять, кто и что прочитал |

## Структура

```
docker-compose.yml     postgres:16-alpine, порт 5433, том + init-скрипты
.env                   параметры подключения для compose и для node-скриптов
sql/01_schema.sql      users, accounts, account_members, operations
sql/02_seed.sql        Анна, Пётр и общий счёт на 1000 ₽
src/config.ts          настройки из окружения
src/db.ts              пул pg, BEGIN с уровнем изоляции, коды конфликтов
src/bank.ts            операции над счётом (чтение, запись, журнал)
src/barrier.ts         FileBarrier: точка встречи агентов разных потоков
src/strategies.ts      read-modify-write / for-update / atomic
src/transfer.ts        повторы по 40001 и итог проводки
src/scenarios.ts       участники и четыре сценария
src/world.ts           мир agents-world из двух агентов
src/runner.ts          один сценарий: сброс → прогон → чтение итога
src/report.ts          таблицы и сводка
src/sleep.ts           пауза для барьера и повторов
agents/bankAgent.ts    агент банка (контракт agents-world)
agents/bankAgentOptions.ts  разбор и проверка настроек агента
scripts/simulate.ts    прогон всех сценариев
scripts/nonRepeatableRead.ts  неповторяющееся чтение на двух сессиях
test/isolation.test.ts проверки против реального PostgreSQL
```

Связи идут в одну сторону: `agents/` знает про `src/`, `src/` — про `pg` и `agents-world`, а библиотека агентов ничего не знает ни про банк, ни про PostgreSQL.

# Roaring Bitmaps (сжатые битовые карты)

## Что это такое

**Roaring Bitmap** — это структура данных для компактного хранения множества
32-битных неотрицательных целых чисел (uint32) с быстрой проверкой
принадлежности, вставкой, удалением и теоретико-множественными операциями.

Главная проблема обычной битовой карты на всё 32-битное пространство в том,
что она занимает фиксированные `2^32` бита (512 МБ), даже если хранится всего
несколько значений. Roaring Bitmap решает эту задачу: память расходуется
пропорционально количеству **реально хранящихся** значений, а операции
остаются быстрыми.

## Как устроен

Всё пространство значений `[0, 2^32 - 1]` делится на «чанки» по
`2^16 = 65536` значений:

- **старшие 16 бит** числа — это ключ чанка (`high`);
- **младшие 16 бит** — хранятся внутри контейнера (`low`).

Например, число `123456` = `0000 0000 0000 0001 | 1110 0010 0100 0000`:

- `high = 1` (чанк номер 1, значения `65536..131071`);
- `low = 57920`.

Снаружи структура — это отображение `high → контейнер`. Создаётся контейнер
только тогда, когда в его чанк попало хотя бы одно значение. Именно это даёт
экономию: пустые чанки не занимают памяти.

## Контейнеры

Внутри чанка младшие 16 бит хранятся в одном из трёх типов контейнеров:

| Тип | Что хранит | Когда выгоден |
|-----|-----------|----------------|
| **ArrayContainer** | отсортированный массив 16-битных значений | разреженные наборы (≤ 4096 элементов) |
| **BitmapContainer** | битовая карта на 65536 бит (2048 слова по 32 бита, фиксированные 8 КБ) | плотные наборы (> 4096 элементов) |
| **RunContainer** | интервалы `[start, start + length)` | длинные непрерывные диапазоны |

Переключение `array ↔ bitmap` происходит **автоматически** на пороге
4096 элементов: при вставке array «разбухает» в bitmap, при удалении bitmap
сжимается обратно в array. Сжатие в `RunContainer` выполняется явным вызовом
`runOptimize()`.

## Основные операции и сложность

| Операция | Метод | Сложность |
|----------|-------|-----------|
| Вставка значения | `add(value)` | O(1) в среднем (поиск чанка по Map + вставка в контейнер) |
| Удаление значения | `remove(value)` | O(1) в среднем |
| Проверка принадлежности | `has(value)` / `contains(value)` | O(1) |
| Количество значений | `size` | O(число контейнеров) |
| Все значения | `toArray()` | O(n), n — число значений |
| Объединение | `union(other)` | O(суммарный размер чанков) |
| Пересечение | `intersection(other)` | O(суммарный размер чанков) |
| Разность | `difference(other)` | O(суммарный размер чанков) |
| Симметрическая разность | `symmetricDifference(other)` | O(суммарный размер чанков) |
| Сжатие диапазонов | `runOptimize()` | O(n) |

## Где применяется

- **Поисковые системы и полнотекстовые индексы** (Apache Lucene): инвертированные
  индексы — хранение ID документов, где встречается термин.
- **Колоночные и аналитические БД** (Druid, ClickHouse, Apache Pinot, Kylin):
  фильтры и пересечения множеств ID.
- **Флаги пользователей и сегменты** в рекламе и аналитике (точное пересечение
  сегментов аудитории).
- **Хранение разреженных множеств** с экономией памяти там, где обычный
  `BitSet`/`Set<number>` слишком затратен.
- Задачи на пересечения/объединения больших целочисленных множеств.

## Отличия от других структур

- **От обычной битовой карты (Bitmap / BitSet)**: Roaring Bitmap не хранит пустые
  чанки, поэтому для разреженных данных занимает на порядки меньше памяти.
- **От `Set<number>` / хеш-таблицы**: сопоставимая скорость, но компактнее и
  умеет эффективные побитовые операции над целыми чанками.
- **От сжатого битового вектора (Compressed Bit Vector)**: использует не один
  способ сжатия, а гибрид из трёх контейнеров, выбирая лучший для каждого чанка.
- **От фильтра Блума**: Roaring Bitmap хранит значения **точно** (без
  ложноположительных срабатываний) и поддерживает удаление и перечисление.

## Недостатки

- Хранит только **неотрицательные целые 32-битные** значения (не строки, не
  произвольные объекты) — их нужно предварительно хешировать/кодировать.
- Не даёт преимущества, если данные равномерно «размазаны» по всему диапазону
  без повторов — тогда контейнеров будет много.
- Реализация со сменой типов контейнеров сложнее, чем у простого `Set`.

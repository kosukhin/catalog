# Фасетный индекс (Facet Index)

## Что это такое

**Фасетный индекс** — это структура данных для **фасетного поиска**: она
позволяет фильтровать документы сразу по нескольким **фасетам** (атрибутам:
бренд, цвет, размер, категория, тег) и одновременно получать **количество
документов для каждого значения** каждого атрибута.

По сути это набор инвертированных индексов по полям, дополненный счётчиками
и семантикой drill-down.

## Как устроен

Хранятся две части:

1. **Прямой индекс** — для удаления и обновления:

   ```
   docId -> { поле -> множество значений }
   ```

2. **Фасетные инвертированные индексы** — по одному на каждое поле:

   ```
   поле -> (значение -> постинг-лист, множество docId)
   ```

Пример. Три товара:

| docId | brand   | color | size |
|-------|---------|-------|------|
| 1     | apple   | black | 6    |
| 2     | samsung | black | 7    |
| 3     | apple   | white | 6    |

Получаются фасеты:

```text
brand: apple   -> {1, 3}   samsung -> {2}
color: black   -> {1, 2}   white   -> {3}
size:  6       -> {1, 3}   7       -> {2}
```

Запрос `color = black` даёт документы `{1, 2}`. Значения одного поля
объединяются через **OR** (мультивыбор), разные поля пересекаются через
**AND**.

## Счётчики и drill-down

### Что такое drill-down

**Drill-down** («проваливание», «углубление») — это последовательное сужение
выборки: пользователь выбирает значение фасета, видит, сколько документов
осталось, и тут же получает счётчики значений — с учётом сделанного выбора
(кроме самого выбранного поля, см. ниже). Так он может «проваливаться»
глубже, не теряя ориентации в том, какие варианты ещё доступны. Термин
пришёл из BI/OLAP, где означает переход от сводного агрегата к более
детальным данным.

Ключевой вопрос, на который отвечает drill-down: **«сколько документов
получится, если я добавлю это значение к текущему фильтру?»** — ещё до того,
как значение выбрано.

### Пример по шагам

Возьмём каталог из примера выше:

| docId | brand   | color | size |
|-------|---------|-------|------|
| 1     | apple   | black | 6    |
| 2     | samsung | black | 7    |
| 3     | apple   | white | 6    |

**Шаг 1. Фильтров нет.** Все три документа в выдаче. Счётчик значения —
это просто размер его постинг-листа:

| brand   | count | color | count | size | count |
|---------|-------|-------|-------|------|-------|
| apple   | 2     | black | 2     | 6    | 2     |
| samsung | 1     | white | 1     | 7    | 1     |

**Шаг 2. Выбран `color = black`.** Выдача сузилась до `{1, 2}`.

Что показывать в фасете `color`? Если считать «честно» по текущей выдаче,
получится `black: 2, white: 0`. Но `white: 0` вводит в заблуждение:
пользователь не поймёт, что белый вариант существует и его можно добавить.
Поэтому для **своего** поля фильтр игнорируется:

| Фасет | Активный фильтр | Что учитывается | Счётчики |
|-------|-----------------|-----------------|----------|
| color | `color = black` | ничего (свой фильтр отброшен) | black: 2, white: 1 |
| brand | —               | `color = black` | apple: 1, samsung: 1 |
| size  | —               | `color = black` | 6: 1, 7: 1 |

Так пользователь видит: «сейчас 2 чёрных товара; если переключиться на
белый — будет 1; если добавить бренд apple — останется 1».

**Шаг 3. Добавлен `brand = apple`.** Выдача — `{1}`. Фасет `color`
по-прежнему игнорирует фильтр по цвету, но учитывает бренд:

| Фасет | Учитываются фильтры | Счётчики |
|-------|---------------------|----------|
| color | `brand = apple` | black: 1, white: 1 |
| brand | `color = black` | apple: 1, samsung: 1 |
| size  | `brand = apple`, `color = black` | 6: 1, 7: 0 |

Теперь видно, что при выбранном бренде apple смена цвета на white сохранит
1 товар, а `size = 7` даст 0 — то есть приведёт к пустой выдаче.

### Правило подсчёта

Для поля `F` и значения `v`:

```text
count(F = v, фильтры) =
    | postings(F, v)
      ∩ ⋂_{g ∈ filters, g ≠ F} ⋃_{u ∈ values(g)} postings(g, u) |
```

Словами:

1. берём постинг-лист значения `v`;
2. из набора фильтров выбрасываем фильтр по самому полю `F`;
3. для каждого оставшегося поля объединяем постинг-листы его выбранных
   значений (OR);
4. пересекаем все полученные множества (AND) и считаем размер.

Именно это делает `counts(field, filters)`:

```js
index.counts('color', { color: 'black' });
// [{ value: 'black', count: 2 }, { value: 'white', count: 1 }]
// фильтр color = black отброшен, поэтому white не обнуляется
```

### Мультивыбор внутри фасета

Внутри одного поля значения объединяются через OR. При выбранных
`color ∈ {black, white}` выдача — `{1, 2, 3}`, а счётчики цветов
по-прежнему считаются **без** фильтра по цвету:

```js
index.search({ color: ['black', 'white'] });   // [1, 2, 3]
index.counts('color', { color: ['black', 'white'] });
// [{ value: 'black', count: 2 }, { value: 'white', count: 1 }]
```

Если бы счётчики учитывали собственный мультивыбор, у выбранных значений
всегда стояло бы одно и то же число, а у невыбранных — 0: фасет перестал
бы подсказывать дальнейшие шаги.

### Почему это важно

- **Навигация без тупиков.** Пользователь видит, какие значения вообще
  существуют в текущей выборке и сколько документов дадут, а не гадает,
  почему всё стало нулевым.
- **Осознанный мультивыбор.** Можно оценить, что даст добавление второго
  значения, ещё до клика.
- **Меньше пустых страниц.** Заранее видно, какие комбинации фильтров
  приведут к пустой выдаче (`count = 0`).
- **Цена.** Счётчики — это дополнительные пересечения постинг-листов,
  поэтому их считают лениво: только для видимых фасетов и с ограничением
  `topValues(field, filters, limit)`.

### Disjunctive faceting

Правило «фильтр по своему полю игнорируется» называется **disjunctive
faceting** (дизъюнктивное фасетирование). Оно есть в Elasticsearch (через
`post_filter` и отдельные агрегации), Solr (отдельные фасетные запросы)
и в большинстве UI-библиотек фасетного поиска. В этой реализации за него
отвечает метод `counts(field, filters)`: он сам исключает `field`
из переданных фильтров.

## Основные операции и сложность

| Операция | Метод | Сложность |
|----------|-------|-----------|
| Добавить документ | `addDocument(docId, attributes)` | O(v), v — число значений атрибутов |
| Удалить документ | `removeDocument(docId)` | O(v) |
| Поиск по фильтрам | `search(filters)` | пересечение постинг-листов, начиная с самых коротких |
| Счётчики значений | `counts(field, filters)` | O(размер постинг-листов поля + пересечения) |
| Топ значений | `topValues(field, filters, limit)` | O(V log V) или O(V log k) через кучу |
| Все значения фасета | `values(field)` | O(V log V) |
| Все документы | `documents()` | O(n log n) |

Здесь `V` — число значений фасета, `n` — число документов.

Постинг-листы часто хранят не как `Set`, а как **битовые карты** или
**Roaring Bitmaps** — тогда пересечение фасетов выполняется побитово и
работает значительно быстрее.

## Где применяется

- Фильтры в интернет-магазинах: бренд, цвет, размер, цена с числом товаров
  рядом с каждым значением.
- Поисковые системы: **Elasticsearch aggregations**, **Solr faceting**,
  Lucene `SortedSetDocValuesFacetCounts`.
- Каталоги фильмов, книг, музыки, вакансий, недвижимости.
- Observability и логи (Kibana, Grafana): фасеты по сервису, уровню лога,
  хосту.
- BI-дашборды и аналитика с быстрым срезом по категориям.

## Отличия от других структур

- **От инвертированного индекса**: там термин → документы для текста; здесь
  структурированный атрибут → документы, плюс счётчики, мультизначные поля
  и drill-down.
- **От хеш-таблицы**: хеш-таблица отдаёт документы по одному ключу; фасетный
  индекс объединяет много полей, пересекает фильтры и агрегирует счётчики.
- **От множества (Set)**: Set отвечает на вопрос «есть ли элемент», а не
  «какие документы обладают значением атрибута».
- **От структур диапазонов**: range-фасеты могут опираться на B-дерево или
  дерево отрезков, но базовая механика фасетов — это доступ по ключу
  и пересечение постинг-листов.

## Недостатки

- Память растёт как сумма постинг-листов по всем парам «поле — значение».
- Плохо подходит для полей с огромной кардинальностью (`id`, timestamp,
  email): почти у каждого значения счётчик равен 1.
- Для удаления и обновления нужен прямой индекс `docId -> значения`.
- При мультивыборе счётчики приходится пересчитывать — это не бесплатная
  операция.
- Это не полнотекстовый поиск, а срез по категориальным атрибутам; обычно
  комбинируется с инвертированным индексом.

# Урок 3.3 — `ReaderT`: Reader-трансформер над другой монадой 🔴

> Цель: научиться комбинировать **окружение** (конфиг, зависимости) с другой
> монадой — отсутствия (`Maybe`), ошибки (`Either`, `Result`) или асинхронности
> с каналом ошибки (`Async`): шаги цепочки видят конфиг и при этом умеют
> безопасно завершаться неуспехом. Ключевые слова: `ReaderT(Monad)`, `ask`,
> `lift`, `liftFn`, `runWith`.
> Все примеры печатают результат в консоль и проверены на crocks 0.12.
>
> Документация: https://crocks.dev/docs/crocks/ReaderT.html
>
> 📦 **Каждый блок в уроке самодостаточен.** Импорты и определения включены:
> скопируй блок в файл `.mjs` в проекте с `crocks` (`npm install crocks`, если
> его ещё нет) и запусти `node файл.mjs`. Примеры с ожидаемыми ошибками
> обёрнуты в `try/catch`, чтобы блок дорабатывал до конца и печатал сообщение.

## 1. Проблема: два контекста сразу

`Reader` (урок 3.2) умеет проносить окружение, но ничего не знает о **неуспехе**
и **асинхронности**. `Maybe` / `Either` / `Async` (уроки 1.1–1.2, 4.1) умеют
представлять такие исходы, но ничего не знают об **окружении**. В реальном коде
они нужны вместе: «возьми id из запроса, найди пользователя в конфиге, достань
его город» — и любой шаг может не найтись.

Наивная попытка склеить их «в лоб» ломается:

```js
import crocks from 'crocks'
const { Reader, getProp } = crocks

const profile = id =>
  Reader(env => getProp(id, env.users))
    .map(user => user.name.toUpperCase())   // ❌ map получил Maybe, а не user

const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }

try {
  console.log(profile(1).runWith(env))
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Cannot read properties of undefined (reading 'toUpperCase')
}
```

`map` у `Reader` сдвигает функцию ровно на один слой (урок 0.1): значение
Reader'а — это `Maybe user`, поэтому `user.name` — `undefined`.

Можно «проткнуть» слой вручную — и это даже работает:

```js
import crocks from 'crocks'
const { Reader, getProp } = crocks

const profile = id =>
  Reader(env => getProp(id, env.users).map(u => u.name.toUpperCase()))

const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }

console.log(profile(1).runWith(env).toString())  // Just "IVAN"
console.log(profile(2).runWith(env).toString())  // Nothing
```

Но композиция разваливается: каждый следующий шаг приходится вручную вкладывать
внутрь `Maybe`, а `Reader.chain` ждёт функцию, возвращающую **Reader**, а не
`Maybe` — ошибка проявится при запуске:

```js
import crocks from 'crocks'
const { Reader, getProp } = crocks

try {
  Reader(env => getProp('1', env.users))
    .chain(user => getProp('city', user))
    .runWith({ users: { 1: { city: 'Москва' } } })
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Reader.chain: Function must return a Reader
}
```

Почему именно `Reader`? Потому что `chain` — операция **конкретного
контейнера**, и её контракт всегда один: `chain :: m a -> (a -> m b) -> m b`.
Следующий шаг обязан вернуть **тот же** `m`, иначе цепочке нечем продолжить
контекст. Это общее правило (урок 0, раздел 4; урок 1.4, таблица терминов):

| Контейнер | `chain` ждёт функцию |
|---|---|
| `Maybe` | `a -> Maybe b` |
| `Either` | `a -> Either e b` |
| `Reader e` | `a -> Reader e b` |
| `ReaderT e (M)` | `a -> ReaderT e (M b)` |

> 📖 **Как читать `chain :: m a -> (a -> m b) -> m b`.**
> `m` — конструктор контейнера (`Maybe`, `Reader e`, `ReaderT e M`);
> `a` и `b` — **типы** значений, а не сами значения. `m a` — «контейнер `m`,
> содержащий значение типа `a`»; `m b` — тот же контейнер со значением типа `b`.
>
> Это **метод-форма**: `m a` здесь — получатель, то есть `m.chain(fn)`. У
> pointfree-функции порядок обратный: `chain :: (a -> m b) -> m a -> m b` —
> сначала функция, контейнер последним (урок 1.4). В Fantasy Land получатель
> отделяют стрелкой `~>`: `chain :: m a ~> (a -> m b) -> m b`.
>
> Конкретно: для `Maybe` — `Maybe a -> (a -> Maybe b) -> Maybe b`;
> для `Reader e` — `Reader e a -> (a -> Reader e b) -> Reader e b`.

```text
Just(5).chain(n => Just(n * 2))

Just(5)            :: Maybe Number              -- это m a, где a = Number
n => Just(n * 2)   :: Number -> Maybe Number    -- это a -> m b
результат          :: Maybe Number              -- это m b, где b = Number
```

У `Reader` это видно по реализации: `chain` запускает следующий шаг с **тем же**
окружением.

```text
// упрощённо, как устроен Reader.chain в crocks
Reader(env => {
  const next = fn(runWith(env))   // fn обязан вернуть Reader
  return next.runWith(env)        // запускаем его с тем же env
})
```

Если `fn` вернул `Maybe`, у результата нет `.runWith(env)` — отсюда
`TypeError`. И поскольку `Reader` ленив (ничего не вычисляет до запуска),
проверка типа результата тоже отложена до `runWith` — поэтому ошибка
проявляется при запуске, а не в момент `chain`.

В уроке 3.2 это правило сформулировано как «`chain` принимает функцию
`a -> Reader`, а не готовый Reader» (раздел 4); здесь важно увидеть **почему**:
возвращаемый Reader — это следующий шаг, который нужно запустить с тем же
окружением.

`ReaderT` решает ровно это: остаётся Reader, но его значение **уже лежит в
монаде**, и `map`/`chain`/`ap` работают сквозь оба слоя. Вот та же задача:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)
const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }

// та же строка, которая падала с Reader:
// map теперь получает user, а не Maybe user
const name = id =>
  MaybeReader(env => getProp(id, env.users))
    .map(user => user.name.toUpperCase())

console.log(name(1).runWith(env).toString()) // Just "IVAN"

// шаг, который снова возвращает Maybe, связывается через chain
// (liftFn — мост из a -> Maybe b в a -> ReaderT; подробно в разделе 5)
const city = id =>
  MaybeReader(env => getProp(id, env.users))
    .chain(user => MaybeReader.liftFn(getProp('city'))(user))
    .map(c => c.toUpperCase())

console.log(city(1).runWith(env).toString()) // Just "МОСКВА"
console.log(city(2).runWith(env).toString()) // Nothing
```

Что изменилось по сравнению с «ручным» вариантом:

- `map` и `chain` применяются к обычному значению (`user`), а не к `Maybe user`:
   протыкать слой вручную больше не нужно;
- шаг, который сам возвращает `Maybe`, встраивается в цепочку через `chain`
   (с адаптером `liftFn`), а не через вложенную лямбду;
- `Nothing` на любом шаге **коротко замыкает** всю цепочку;
- обработка отсутствия остаётся на конце — после `runWith(env)`
   (`.option(...)`, `.either(...)`).

Синтаксис `ReaderT`, `liftFn` и `runWith` разберём в следующих разделах —
сейчас важно увидеть, что форма кода осталась прежней, а композиция заработала.

## 2. Форма: `ReaderT(Monad)` и `runWith`

`ReaderT` — **конструктор конструктора** (type constructor):

```text
ReaderT :: Monad M => M -> Reader(M) e (m a)
```

Разберём запись по частям:

| Обозначение | Что означает | Пример |
|---|---|---|
| `M` | TypeRep внутренней монады | `Maybe` |
| `e` | тип окружения (environment) | `{ api: string }` |
| `m` | та же монада в записи результата (`M` и `m` — одна монада) | `Maybe` |
| `a` | тип успешного значения | `User` |
| `m a` | значение типа `a` внутри монады `m` | `Maybe User` |
| `Reader(M) e (m a)` | вычисление «окружение → монадическое значение», то есть `e -> m a` | `Config -> Maybe User` |

> 📖 Скобки в `(m a)` нужны потому, что `m a` — это применение конструктора
> `m` к типу `a`. Без них запись `Reader(M) e m a` распалась бы на четыре
> отдельных аргумента. В JavaScript статических типов нет, поэтому всё это —
> **документационная нотация**: `Reader(Maybe) e (Maybe a)` на практике — просто
> функция `env => Maybe a`.

Он принимает **TypeRep** — конструктор любой монады (`Maybe`, `Either`,
`Result`, `Async`, `Identity`) — и возвращает новый конструктор.

> 📖 **TypeRep** (type representative, «представитель типа») — это **сам
> конструктор** `Maybe` / `Either` / `Async`, а не его значение. Именно у
> конструктора есть статические `of`, `type()` и `@@type`, которые `ReaderT`
> использует, чтобы создавать значения и сравнивать типы. Поэтому правильно —
> `ReaderT(Maybe)`, а не `ReaderT(Just(1))`.

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

// Maybe — конструктор (TypeRep), Just(1) — его значение
console.log(typeof Maybe)          // 'function'
console.log(Maybe.type())          // 'Maybe'
console.log(typeof Maybe.of)       // 'function'

const MaybeReader = ReaderT(Maybe)
console.log(MaybeReader.type())                     // 'Reader( Maybe )'
console.log(MaybeReader.of(1).runWith().toString()) // Just 1
```

Тот, в свою очередь, принимает функцию `env -> M a`:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)          // Reader( Maybe )

const findUser = id =>
  MaybeReader(env => getProp(id, env.users))

const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }

console.log(findUser(1).runWith(env).toString()) // Just { name: "Ivan", city: "Москва" }
console.log(findUser(2).runWith(env).toString()) // Nothing
```

Формально `ReaderT e (m a)` — это то же самое, что `e -> m a`. Отличие от
«ручного» `Reader(env => Maybe a)` — в методах: они поднимаются **через**
внутреннюю монаду, а не остаются на верхнем слое.

Как выглядит тип:

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)

console.log(MaybeReader.type())    // 'Reader( Maybe )'
console.log(MaybeReader['@@type']) // 'crocks/Reader@1( crocks/Maybe@4 )'
console.log(String(MaybeReader.of(1))) // 'Reader( Maybe ) Function'
```

⚠️ **`ReaderT` требует именно монаду.** Не любой объект с `map`/`chain`:

```js
import crocks from 'crocks'
const { ReaderT } = crocks

try {
  ReaderT({})
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: ReaderT: Monad required for construction
}
```

**Обёрнутая функция обязана вернуть монаду** — ровно ту, над которой построен
ReaderT. Проверка происходит при `runWith`:

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)

try {
  MaybeReader(() => 42).runWith({})
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Reader( Maybe ): Maybe must be returned by wrapped function
}

try {
  MaybeReader()
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Reader( Maybe ): Maybe returning function required
}
```

## 3. `of` и `ask`

### `of` — значение, окружение не нужно

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)

console.log(MaybeReader.of('nice').runWith().toString())  // Just "nice"
console.log(MaybeReader.of('nice').runWith({ any: 'env' }).toString()) // Just "nice"
```

`of` кладёт значение в `Maybe` и полностью игнорирует окружение.

### `ask()` — окружение как значение

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)

console.log(MaybeReader.ask().runWith(76).toString())  // Just 76
console.log(MaybeReader.ask().runWith({ name: 'Ivan' }).toString()) // Just { name: "Ivan" }
```

### `ask(fn)` — окружение, преобразованное функцией

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)
const add = x => y => x + y

console.log(MaybeReader.ask(e => e.name).runWith({ name: 'Ivan' }).toString()) // Just "Ivan"
console.log(MaybeReader.ask(add(10)).runWith(76).toString())                  // Just 86
```

⚠️ **`ask(fn)` оборачивает результат через `Monad.of`, а не проверяет его.**
В документации сказано, что функция «должна вернуть тип монады», но исходник
0.12 делает `ReaderT(Monad.of).map(fn)` — то есть `fn` возвращает **обычное
значение**, и уже оно попадает в `Monad.of`. Проверено:

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)

console.log(MaybeReader.ask(x => Maybe.of(x + 1)).runWith(1).toString())
// Just Just 2 — двойная обёртка
```

Отсюда главная ловушка: `ask` **не** умеет «не найти» значение. Если функция
вернула `undefined`, получится `Just undefined`, а не `Nothing`:

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)
const env = { users: {} }

console.log(MaybeReader.ask(cfg => cfg.users[99]).runWith(env).toString())
// Just undefined — НЕ Nothing!

console.log(MaybeReader.ask(cfg => cfg.users[99]).runWith(env).option('нет'))
// undefined — значение «есть», просто пустое
```

Для поиска с отсутствием используй монадическую функцию через `liftFn`
(раздел 5) или конструктор с `safe`/`getProp`:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, safe, isNumber } = crocks

const MaybeReader = ReaderT(Maybe)

console.log(MaybeReader(safe(isNumber)).runWith(76).toString())   // Just 76
console.log(MaybeReader(safe(isNumber)).runWith('76').toString()) // Nothing
```

## 4. `map` и `chain` — шаги, которые могут не найтись

`map` применяет функцию к значению **внутри** внутренней монады, а `chain`
«сплющивает» её, если шаг снова вернул ReaderT:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)
const findUser = id => MaybeReader(env => getProp(id, env.users))

const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }
const toUpper = s => s.toUpperCase()

console.log(findUser(1).map(u => u.name).map(toUpper).runWith(env).toString()) // Just "IVAN"
console.log(findUser(2).map(u => u.name).map(toUpper).runWith(env).toString()) // Nothing
```

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)
const findUser = id => MaybeReader(env => getProp(id, env.users))
const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }

const getCity = user => MaybeReader.liftFn(getProp('city'))(user)

console.log(findUser(1).chain(getCity).runWith(env).toString()) // Just "Москва"
console.log(findUser(2).chain(getCity).runWith(env).toString()) // Nothing
```

`Nothing` **коротко замыкает** цепочку: ни `map`, ни `chain` не вызываются —
ровно как у обычного `Maybe` (урок 1.1).

⚠️ **`chain` у ReaderT ждёт функцию `a -> ReaderT`, а не `a -> M`.**
Это самая частая ошибка при переходе с `Maybe`:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)
const findUser = id => MaybeReader(env => getProp(id, env.users))
const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }

try {
  findUser(1).chain(user => getProp('city', user)).runWith(env)
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Reader( Maybe ).chain: Function must return a Reader( Maybe )
}
```

Причём `chain` **ленив**: сам вызов ошибку не бросает, TypeError случится
только при `runWith` — проверка типа результата живёт внутри запуска.
Зато аргумент-не-функция проверяется сразу:

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks

const MaybeReader = ReaderT(Maybe)

try {
  MaybeReader.of(1).chain(42)
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Reader( Maybe ).chain: Reader( Maybe ) returning function required
}
```

Мост из «простой» монадической функции `a -> M b` в `a -> ReaderT` — это
`liftFn` из следующего раздела.

## 5. `lift` и `liftFn` — мост из внутренней монады в ReaderT

### `lift(m)` — поднять готовое значение

Если значение в монаде уже есть (например, пришло из другого места программы),
его не нужно «пересчитывать» от окружения:

```js
import crocks from 'crocks'
const { ReaderT, Maybe } = crocks
const { Just, Nothing } = Maybe

const MaybeReader = ReaderT(Maybe)

console.log(MaybeReader.lift(Just(5)).runWith({ any: 'env' }).toString())  // Just 5

// неуспех «проносится» дальше, map его не трогает
console.log(MaybeReader.lift(Nothing()).map(x => x + 1).runWith({ any: 'env' }).toString())
// Nothing
```

`lift` принимает только **ту же** монаду, над которой построен ReaderT:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, Either } = crocks

const MaybeReader = ReaderT(Maybe)

try {
  MaybeReader.lift(Either.Right(1))
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Reader( Maybe ).lift: Maybe instance required
}
```

### `liftFn(fn)` — поднять функцию `a -> M b`

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)

const readName = MaybeReader.liftFn(getProp('name'))

console.log(readName({ name: 'Ivan' }).runWith(null).toString()) // Just "Ivan"
console.log(readName({}).runWith(null).toString())              // Nothing
console.log(readName(10).runWith(null).toString())              // Nothing
```

`liftFn` каррирован, поэтому работают обе формы:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)

console.log(MaybeReader.liftFn(getProp('name'), { name: 'Ivan' }).runWith(null).toString())
// Just "Ivan"
```

⚠️ **И `lift`, и `liftFn` игнорируют окружение.** Они не читают `env` из
`runWith`: значение уже готово (`lift`) или вычисляется из **явного**
аргумента (`liftFn`). Проверено:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)
const readName = MaybeReader.liftFn(getProp('name'))

console.log(readName({ name: 'Ivan' }).runWith({ name: 'Olga' }).toString())
// Just "Ivan"
```

Чтобы прочитать окружение **и** получить монаду, комбинируй `ask()` и
`liftFn`:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)

console.log(
  MaybeReader.ask()
    .chain(MaybeReader.liftFn(getProp('name')))
    .runWith({ name: 'Ivan' }).toString()
)
// Just "Ivan"
```

Здесь `ask()` даёт `Just env`, `chain` передаёт `env` в `liftFn(getProp('name'))`,
а тот строит ReaderT с `Maybe name`. Окружение при этом уже использовано —
повторный `runWith` его проигнорирует.

## 6. `ap` и `liftA2` — несколько чтений окружения

Аппликатив ReaderT позволяет скомбинировать несколько вычислений, которые
читают **одно и то же** окружение. Если внутренняя монада — `Result`, ошибки
накапливаются (поведение `Result.ap` из урока 1.2):

```js
import crocks from 'crocks'
const { ReaderT, Result, Pair, ifElse, isNumber, liftA2, fst, snd } = crocks

const { Ok, Err } = Result
const ResultReader = ReaderT(Result)

const add = x => y => x + y
const makeErr = x => Err([`${x} is not a Number`])
const isValid = ResultReader.liftFn(ifElse(isNumber, Ok, makeErr))

// окружение — Pair(первое значение, второе значение) из урока 2.1
const first = ResultReader.ask(fst).chain(isValid)
const second = ResultReader.ask(snd).chain(isValid)

console.log(ResultReader.of(add).ap(first).ap(second).runWith(Pair(34, 21)).toString())
// Ok 55

console.log(first.map(add).ap(second).runWith(Pair(true, 21)).toString())
// Err [ "true is not a Number" ]

console.log(liftA2(add, first, second).runWith(Pair('Bob', 'Jones')).toString())
// Err [ "Bob is not a Number", "Jones is not a Number" ]
```

Обрати внимание: `ap` — это **не** способ передать окружение (как и у обычного
`Reader`, урок 3.2). Окружение подаётся только `runWith`, а `ap`/`liftA2`
лишь комбинируют вычисления, которые позже увидят один общий `env`.

⚠️ Обе стороны `ap` должны быть ReaderT **одного типа**:

```js
import crocks from 'crocks'
const { ReaderT, Maybe, Either } = crocks

const MaybeReader = ReaderT(Maybe)
const EitherReader = ReaderT(Either)

try {
  MaybeReader.of(x => x).ap(EitherReader.of(1))
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: Reader( Maybe ).ap: Reader( Maybe ) required
}
```

## 7. Полный пример: профиль пользователя

Собираем всё вместе: окружение — «база пользователей», каждый шаг может не
найтись, а обработка отсутствия — уже после запуска, методами `Maybe`.

```js
import crocks from 'crocks'
const { ReaderT, Maybe, getProp } = crocks

const MaybeReader = ReaderT(Maybe)

// id -> ReaderT env (Maybe User)
const getUser = id => MaybeReader(cfg => getProp(id, cfg.users))

// User -> ReaderT env (Maybe City)
const getCity = user => MaybeReader.liftFn(getProp('city'))(user)

// id -> ReaderT env (Maybe City)
const city = id =>
  getUser(id)
    .chain(getCity)
    .map(c => c.toUpperCase())

const env = { users: { 1: { name: 'Ivan', city: 'Москва' } } }

console.log(city(1).runWith(env).toString())  // Just "МОСКВА"
console.log(city(2).runWith(env).toString())  // Nothing — пользователя нет

// неуспех обрабатывается у внутренней монады, а не у ReaderT
console.log(city(2).runWith(env).option('город не указан'))
// 'город не указан'

// тот же код — другой конфиг
console.log(city(1).runWith({ users: { 1: { city: 'Казань' } } }).toString())
// Just "КАЗАНЬ"
```

Что здесь важно:

- `city` — **описание** вычисления; ни один шаг не выполняется до `runWith`;
- `Nothing` на любом шаге замыкает цепочку, и следующие шаги не вызываются;
- окружение не «зашито» в функцию — один и тот же `city` обслуживает разные
   конфиги;
- «что делать при отсутствии» решается в конце (`option`, `either`, `alt`),
   а не внутри бизнес-логики.

## 8. `ReaderT(Async)`: конфиг + асинхронность

Внутренней монадой может быть `Async` (урок 4.1). Тогда получается вычисление,
которому нужен конфиг и которое завершается асинхронно.

> 📖 **`Async` — не «монада сбоя».** Это монада асинхронного вычисления с двумя
> исходами: `Resolved` (успех) и `Rejected` (отказ). Ошибка здесь — лишь одна из
> веток, а не суть типа. Сходство с `Maybe`/`Either` в другом: у всех есть
> **неуспешная ветка**, на которой `chain` коротко замыкается.

```js
import crocks from 'crocks'
const { ReaderT, Async } = crocks

const AsyncReader = ReaderT(Async)

const fetchUser = url => Async.of({ id: 1, name: 'Ivan', from: url })

const program = AsyncReader.ask(e => e.api)
  .map(api => api + '/users/1')
  .chain(url => AsyncReader.liftFn(fetchUser)(url))
  .map(u => `${u.name} @ ${u.from}`)

program
  .runWith({ api: 'https://api.x/v1' })
  .fork(
    e => console.error('rejected:', e.message),
    v => console.log('resolved:', v)
  )
// resolved: Ivan @ https://api.x/v1/users/1
```

⚠️ **`ReaderT(Async)` — это не `Async`.** У него нет `fork`, `toPromise` и
остальных методов `Async`: сначала `runWith(env)` возвращает `Async`, и уже
у него вызывается `fork`:

```js
import crocks from 'crocks'
const { ReaderT, Async } = crocks

const AsyncReader = ReaderT(Async)
const fetchUser = url => Async.of({ id: 1, name: 'Ivan', from: url })

const program = AsyncReader.ask(e => e.api)
  .map(api => api + '/users/1')
  .chain(url => AsyncReader.liftFn(fetchUser)(url))
  .map(u => `${u.name} @ ${u.from}`)

try {
  program.fork(
    e => console.error('rejected:', e.message),
    v => console.log('resolved:', v)
  )
} catch (e) {
  console.log(e.name + ': ' + e.message)
  // TypeError: program.fork is not a function
}
```

Отказ внутренней монады проходит сквозь `map`/`chain`:

```js
import crocks from 'crocks'
const { ReaderT, Async } = crocks

const AsyncReader = ReaderT(Async)

const failing = AsyncReader.lift(Async.Rejected(new Error('network')))

failing
  .map(x => x + 1)            // не выполнится
  .runWith({})
  .fork(
    e => console.error('rejected:', e.message),
    v => console.log('resolved:', v)
  )
// rejected: network
```

Аппликатив запускает независимые вычисления **параллельно** (`Async.ap`), в
отличие от `chain`, который выстраивает их последовательно:

```js
import crocks from 'crocks'
const { ReaderT, Async, curry } = crocks

const AsyncReader = ReaderT(Async)
const delay = (ms, v) => Async((rej, res) => setTimeout(() => res(v), ms))

const a = AsyncReader.lift(delay(100, 'A'))
const b = AsyncReader.lift(delay(100, 'B'))

AsyncReader.of(curry((x, y) => x + y))
  .ap(a)
  .ap(b)
  .runWith({})
  .fork(console.error, v => console.log('ap:', v))     // 'AB' примерно за 100 мс

a.chain(x => b.map(y => x + y))
  .runWith({})
  .fork(console.error, v => console.log('chain:', v))  // 'AB' примерно за 200 мс
```

## 9. ReaderT vs Reader: что выбирать

| | `Reader` (3.2) | `ReaderT(M)` |
|---|---|---|
| Форма | `e -> a` | `e -> M a` |
| Что вернёт `runWith(e)` | значение `a` | монаду `M a` |
| Неуспешная ветка | не выражается | `Nothing` / `Left` / `Rejected` |
| `map(f)` | по значению | по значению **внутри** `M` |
| `chain(f)` ждёт | `a -> Reader` | `a -> ReaderT` |
| Готовое `M a` | — | `lift(m)` |
| Функция `a -> M b` | — | `liftFn(fn)` |
| Обработка неуспеха | — | после `runWith` — методами `M` |
| Типичное применение | конфиг, DI | конфиг + отсутствие/ошибка/асинхронность |

**Правило выбора:**

- нужен только конфиг → `Reader`;
- конфиг **и** возможность «не найтись» → `ReaderT(Maybe)`;
- конфиг **и** причина ошибки → `ReaderT(Either)` / `ReaderT(Result)`;
- конфиг **и** асинхронность → `ReaderT(Async)`;
- конфига нет, есть только отсутствие/ошибка/асинхронность → обычные
   `Maybe` / `Either` / `Async`.

Если `M` — `Identity`, `ReaderT(Identity)` ведёт себя как обычный `Reader`:
внутренний слой ничего не добавляет.

## 10. Чего нет в crocks 0.12 (проверено)

`ReaderT` — намеренно минимальный тип. У экземпляра есть только:

```text
runWith, of, map, ap, chain   (+ toString / inspect / type / valueOf и fantasy-land-алиасы)
```

Статические методы конструктора:

```text
type, of, ask, lift, liftFn
```

Чего **нет** (проверено: `undefined`):

- методов `alt`, `bimap`, `either`, `option`, `coalesce`, `concat`;
- методов внутренней монады — `fork`, `toPromise` и т. п.;
- статического `asks` — его роль играет `ask(fn)` (с оговоркой из раздела 3);
- статических `runReaderT` / `runReaderTWith` — запуск только через `runWith`.

Что при этом **работает**:

- pointfree `runWith(env)(readerT)` — функция просто вызывает `.runWith`;
- `pipeK(f, g, ...)` для функций `a -> ReaderT` (как у `Reader`, урок 3.2):

```js
import crocks from 'crocks'
const { ReaderT, Maybe, pipeK } = crocks

const MaybeReader = ReaderT(Maybe)
const step1 = n => MaybeReader.of(n * 2)
const step2 = n => n > 10 ? MaybeReader.of(n) : MaybeReader.lift(Maybe.Nothing())

console.log(pipeK(step1, step2)(6).runWith({}).toString())  // Just 12
console.log(pipeK(step1, step2)(2).runWith({}).toString())  // Nothing
```

⚠️ __Про импорт в нативном ESM.__ Документация пишет
`import ReaderT from 'crocks/Reader/ReaderT'`, но Node в режиме ESM не
достраивает расширения: получишь `ERR_MODULE_NOT_FOUND`. Рабочий вариант —
с расширением:

```js
import ReaderT from 'crocks/Reader/ReaderT.js'

console.log(typeof ReaderT) // 'function'
```

Либо, как во всех уроках, бери её из главного экспорта:
`const { ReaderT } = crocks`.

## 11. Резюме урока

| Инструмент | Роль |
|---|---|
| `ReaderT(M)` | конструктор ReaderT над монадой `M` |
| `MReader(env => M a)` | описание вычисления: окружение + возможный неуспех |
| `.runWith(env)` / `runWith(env)(readerT)` | запуск → `M a` |
| `MReader.of(x)` | `M.of(x)`, окружение игнорируется |
| `MReader.ask()` | окружение как значение: `M env` |
| `MReader.ask(fn)` | `M (fn env)`; `fn` возвращает **обычное** значение |
| `MReader.lift(m)` | поднять готовую `M a` (окружение игнорируется) |
| `MReader.liftFn(fn)` / `liftFn(fn, x)` | поднять `a -> M b` (окружение игнорируется) |
| `.map(f)` | преобразовать значение **внутри** `M` |
| `.chain(f)`, `f: a -> ReaderT` | следующий шаг: и окружение, и неуспех |
| `.ap(m)` / `liftA2` | несколько чтений одного окружения |
| `.runWith(env).option/either/fork` | обработка неуспеха — уже методами `M` |

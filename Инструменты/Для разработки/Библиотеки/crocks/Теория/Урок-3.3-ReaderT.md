# Теория к уроку 3.3 — `ReaderT`

> **О чём:** почему монады не складываются сами по себе и зачем понадобились монадные трансформеры.
>
> Практика: [`../Урок-3.3-ReaderT.md`](../Урок-3.3-ReaderT.md)

## 1. Проблема

`Reader` умеет читать окружение. `Maybe` умеет представлять отсутствие. `Either` — ошибку. `Async` — асинхронность. Но в реальной функции часто нужно **сразу несколько эффектов**:

- прочитать конфигурацию;
- найти пользователя, которого может не быть;
- вернуть ошибку, если данных нет;
- сделать асинхронный запрос.

Наивная комбинация выглядит как `Reader r (Maybe a)` или `Maybe (Reader r a)`. Обе структуры неудобны: в первой нужно «проваливаться» через два слоя, во второй нельзя вернуть `Nothing` до получения окружения. А главное — **монады не композируются автоматически**: из двух монад не получается третья «бесплатно».

## 2. История

### 2.1. Монадные трансформеры: 1995

В 1995 году Шэн Лян, Пол Худак и Марк Джонс опубликовали статью «Monad Transformers and Modular Interpreters» (POPL). Идея: для многих монад `M` построить `T` такое, что `T m` — новая монада, которая добавляет эффект `M` к базовой монаде `m`. Так из `Reader`, `State`, `Maybe`, `Either` собираются **стеки**.

В Haskell это вылилось в пакеты `transformers` (сами трансформеры) и `mtl` (классы и удобные функции). `ReaderT r m a` — стандартный трансформер Reader:

```haskell
newtype ReaderT r m a = ReaderT { runReaderT :: r -> m a }
```

### 2.2. Зачем это нужно

Без трансформеров пришлось бы вручную писать комбинации вроде «Reader + Maybe + IO» и заново доказывать законы. Трансформеры дают готовые конструкции и общий интерфейс `lift`, который поднимает вычисление из базовой монады в стек.

## 3. Теория

```text
ReaderT r m a = r -> m a
```

- `r` — окружение;
- `m` — базовая монада (например, `Maybe`, `Either e`, `Async`);
- `a` — результат.

`ReaderT` — это `Reader`, у которого результат уже «завёрнут» в `m`. `runReaderT` принимает окружение и возвращает вычисление в `m`.

```text
ask   :: Monad m => ReaderT r m r
lift  :: Monad m => m a -> ReaderT r m a
```

- `ask` возвращает окружение.
- `lift` поднимает действие из `m` в `ReaderT`, не трогая окружение.
- `chain` передаёт окружение дальше и связывает вычисления внутри `m`.

### Порядок имеет значение

`ReaderT r Maybe a` — это `r -> Maybe a`: сначала окружение, потом возможное отсутствие. А `MaybeT (State s) a` — это `s -> (Maybe a, s)`: переход состояния происходит всегда, а результат может быть `Nothing`. Это разные типы с разным поведением, хотя оба «содержат» `Maybe`. Поэтому в стеке трансформеров важен порядок.

### Законы

`ReaderT` должен подчиняться законам монады и закону трансформера: `lift` сохраняет `return` и `bind` базовой монады. Если `lift` ведёт себя странно, весь стек теряет предсказуемость.

## 4. Почему это полезно в JavaScript

- **Конфигурация + ошибки.** `ReaderT config (Either error)` позволяет читать конфиг и возвращать типизированные ошибки без вложенных `if`.
- **Конфигурация + асинхронность.** `ReaderT config Async` избавляет от ручной передачи конфига в каждую асинхронную функцию.
- **Тестируемость.** `runReaderT(computation, mockConfig)` подменяет окружение, не трогая код.
- **Единый стиль.** Вместо зоопарка `async function` с `try/catch` — цепочка `chain`, где эффекты описаны типом.

## 5. Границы

- Стеки трансформеров быстро становятся сложными: `ReaderT r (StateT s (Either e Async))` читать нелегко.
- `lift` добавляет шум; в Haskell его частично прячут за классами `mtl`, в JS такого удобства нет.
- Не для каждой монады есть трансформер; не все эффекты композируются красиво.
- Порядок слоёв влияет на семантику; ошибка в порядке проявляется не сразу.
- В `crocks` `ReaderT` — учебный инструмент; в прикладном JS часто достаточно `Async` + явной передачи конфигурации.

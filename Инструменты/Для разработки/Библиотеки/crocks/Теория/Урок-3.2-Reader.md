# Теория к уроку 3.2 — `Reader`

> **О чём:** как передавать окружение, не протаскивая его через каждый вызов, и почему «функция из окружения» — это монада.
>
> Практика: [`../Урок-3.2-Reader.md`](../Урок-3.2-Reader.md)

## 1. Проблема

Почти любому приложению нужно **окружение**:

- конфигурация (URL, таймауты, флаги);
- зависимости (клиент БД, логгер, HTTP-клиент);
- контекст запроса (пользователь, tenant, locale).

Если передавать окружение явно, каждая функция в цепочке получает лишний параметр:

```js
getUser(db, config, user) -> ...
getOrders(db, config, userId) -> ...
```

Параметр `config` проходит через десятки функций, хотя большинство из них его не использует. Это шум, который мешает читать сигнатуры и менять зависимости.

`Reader` прячет окружение: вычисление описывается как функция `r -> a`, а `chain` автоматически передаёт одно и то же окружение всем шагам.

## 2. История

### 2.1. Функция как монада

В Haskell есть монада для типа функции `(->) r`:

```haskell
instance Monad ((->) r) where
  return x = \_ -> x
  m >>= f  = \r -> f (m r) r
```

Читается так: `return` игнорирует окружение; `bind` передаёт окружение и в исходное вычисление, и в функцию, которая строит следующее. Это и есть `Reader`.

`Reader` — одна из старейших и простейших монад: она не добавляет новых данных, а лишь фиксирует форму «зависимость от окружения». В Haskell она живёт в `Control.Monad.Reader` (пакет `mtl`) и в `ReaderT` (пакет `transformers`).

### 2.2. От Reader к ReaderT

Чистый `Reader` умеет только читать окружение. Если внутри нужно ещё `Maybe`, `Either` или `Async`, используют `ReaderT r m a = r -> m a` — трансформер, который добавляет окружение к другой монаде. Подробнее — в теории к уроку 3.3.

## 3. Теория

```text
Reader r a = r -> a
```

- `r` — тип окружения;
- `a` — тип результата;
- вычисление — это функция, которая ждёт окружение.

Операции:

```text
ask   :: Reader r r
asks  :: (r -> a) -> Reader r a
local :: (r -> r) -> Reader r a -> Reader r a
runReader :: Reader r a -> r -> a
```

- `ask` возвращает окружение целиком.
- `asks(f)` возвращает проекцию окружения: `asks(prop('db'))`.
- `local(f)` меняет окружение для вложенного вычисления (в `crocks` может называться иначе или отсутствовать; идейно это важно).
- `runReader` запускает вычисление с конкретным окружением.

Законы следуют из законов монады функции. Главное свойство: все шаги `chain` видят **одно и то же** окружение, если его не изменить через `local`.

## 4. Почему это полезно в JavaScript

- **Dependency Injection без фреймворка.** Вместо глобального синглтона вычисление принимает зависимости явно, но не в каждой функции.
- **Тесты.** Достаточно вызвать `runReader(computation, mockEnv)`; не нужно подменять модули.
- **Конфигурация.** `asks` позволяет достать нужный кусок конфигурации, не передавая весь объект.
- **Композиция.** `Reader` хорошо соединяется с `Either`/`Maybe` через `ReaderT`, не превращая код в лестницу колбэков.

## 5. Границы

- `Reader` — только **чтение**. Для изменения состояния нужен `State`.
- Окружение одно; если нужны два независимых контекста, их обычно объединяют в один объект или используют несколько `ReaderT`.
- `Reader` не решает проблему жизненного цикла зависимостей (создание, закрытие соединений) — это всё равно делает внешний код.
- В JS нет do-нотации; длинные цепочки `chain` могут быть громоздкими.
- Если функция использует только одну зависимость, иногда проще передать её напрямую, чем строить `Reader`.

# Теория к уроку 3.1 — `State`

> **О чём:** как менять состояние, не изменяя ничего, и почему это вообще возможно.
>
> Практика: [`../Урок-3.1-State.md`](../Урок-3.1-State.md)

## 1. Проблема

Обычное состояние в императивном коде — это переменная, которую меняют по ходу выполнения:

```js
let count = 0
count++
```

Проблемы начинаются, когда таких переменных много и они разделяются между функциями:

- непонятно, кто и когда изменил значение;
- тесты зависят от порядка вызовов;
- параллельные вычисления конфликтуют;
- функцию нельзя переиспользовать без «подготовки мира».

Можно передавать состояние явно: `step(state) -> [newState, result]`. Но тогда каждый вызов нужно вручную связывать с предыдущим, и код превращается в цепочку вида `let [s1, a] = f(s0); let [s2, b] = g(s1); ...`.

`State` — это абстракция, которая прячет это протаскивание состояния, оставляя вычисление чистым.

## 2. История

### 2.1. State monad в Haskell

В Haskell состояние нельзя менять: значения иммутабельны. Поэтому состояние передают явно. Монада `State` инкапсулирует эту передачу:

```haskell
newtype State s a = State { runState :: s -> (a, s) }
```

`runState` принимает начальное состояние и возвращает результат вместе с новым состоянием. `get`, `put`, `modify` — базовые операции; `evalState` и `execState` достают только результат или только состояние.

Монада `State` описана в классических работах по монадам для функционального программирования (Могги, Уодлер) и входит в стандартную экосистему Haskell (`mtl`, `transformers`). `StateT` — её трансформерная версия.

### 2.2. Зачем это математике

В теории категорий состояние связано с произведением: функтор `S × -` (поставить состояние рядом) и экспонента `(-)^S` (функция из состояния) образуют сопряжение. Монада состояния — это монада, порождённая этим сопряжением. Отсюда и формула `s -> (a, s)`.

Для практики важно другое: состояние — это **значение**, а не место в памяти. Его можно передавать, копировать, откатывать, сравнивать. Это делает вычисления детерминированными и тестируемыми.

## 3. Теория

```text
State s a = s -> (a, s)
```

- `s` — тип состояния;
- `a` — тип результата;
- вычисление получает состояние и возвращает пару «результат, новое состояние».

Операции:

```text
get    :: State s s
put    :: s -> State s ()
modify :: (s -> s) -> State s ()
runState :: State s a -> s -> (a, s)
evalState :: State s a -> s -> a
execState :: State s a -> s -> s
```

`chain` связывает вычисления, передавая новое состояние следующему шагу. `map` меняет только результат. `of` возвращает значение, не трогая состояние.

Законы — обычные законы монады; они гарантируют, что порядок связывания не влияет на смысл, а `get`/`put` подчиняются классическим законам состояния (например, `put(s)` дважды эквивалентно одному `put(s)`).

## 4. Почему это полезно в JavaScript

- **Тестируемость.** `runState(computation, initialState)` — чистая функция; не нужно поднимать глобальные переменные.
- **Явные переходы.** Видно, какие шаги меняют состояние, а какие только читают.
- **Парсеры, счётчики, генераторы, игры.** Везде, где есть «мир», который меняется шаг за шагом.
- **Откат и ветвление.** Можно сохранить состояние и вернуться к нему; с мутацией это сложнее.
- **Композиция.** `State` можно комбинировать с `Reader`, `Either`, `Async` через трансформеры.

## 5. Границы

- `State` — не «общее изменяемое состояние» для нескольких потоков. Это чистая эмуляция состояния в одном вычислении.
- Для большого состояния копирование может быть дорогим; нужны персистентные структуры или `ST`-подобные оптимизации.
- В JS нет do-нотации; цепочки `chain` могут быть многословными.
- Если состояние нужно только читать, `Reader` проще. Если нужно только накапливать лог, `Pair`/`Writer` проще.

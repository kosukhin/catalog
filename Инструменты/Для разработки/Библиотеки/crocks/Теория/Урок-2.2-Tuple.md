# Теория к уроку 2.2 — `Tuple`

> **О чём:** зачем нужен типизированный кортеж фиксированной длины, если в JavaScript уже есть массивы и объекты.
>
> Практика: [`../Урок-2.2-Tuple.md`](../Урок-2.2-Tuple.md)

## 1. Проблема

В JS есть два привычных способа хранить несколько значений:

- **массив** — но у него произвольная длина, нет гарантии, что элементы одного типа, и `arr[1]` ничего не говорит о смысле;
- **объект** — но имена полей легко опечатать, порядок не гарантирован, а «обязательность» полей не выражена.

Иногда нужно именно **позиционное** значение фиксированной длины: пара «координаты», тройка «цвет RGB», результат `[ошибка, данные]`, запись без имён. `Tuple` даёт такую структуру: длина известна, позиции пронумерованы, а операции явно говорят, что можно делать с элементами.

## 2. История

### 2.1. Кортежи в ML и Haskell

В ML и Haskell кортеж — встроенный тип-произведение: `(Int, String)`, `(a, b, c)`. Он отличается от списка: длина фиксирована, элементы могут быть разных типов. Компилятор знает арность, а pattern matching позволяет разобрать кортеж по позициям.

С точки зрения теории это n-арное произведение: `A × B × C`. Проекции `fst`/`snd` для пары обобщаются на `project` для n-арного случая.

### 2.2. `Tuple` в `crocks`

`Tuple` появился в `crocks` позже базовых типов (в исходниках указан 2018 год и автор Karthik Iyengar). Это не «ещё один `Pair`», а именно n-арный кортеж: `Tuple(1, 'a', true)`, `Tuple(1, 2)` и т.д.

В отличие от `Pair`, `Tuple` не является монадой. У него есть `map` (по последнему элементу), `concat` (поэлементно, если элементы — полугруппы), `equals`, `project`, `merge`, `mapAll`, `toArray`. Этого достаточно для positional-данных, но недостаточно для «контекста», как у `Pair`.

## 3. Теория

`Tuple` — n-арное произведение. Для длины `n`:

```text
Tuple a1 a2 ... an
```

Операции в `crocks`:

- `map(f)` применяет `f` только к **последнему** элементу; остальные сохраняются. Это соответствует функтору на «хвосте» кортежа.
- `concat(t)` поэлементно объединяет два кортежа одинаковой длины; каждый элемент должен быть полугруппой того же типа.
- `project(i)` возвращает элемент по индексу (с 1).
- `merge(f)` применяет функцию ко всем элементам сразу: `f(a1, ..., an)`.
- `mapAll(f1, ..., fn)` применяет отдельную функцию к каждой позиции.
- `toArray()` отдаёт копию элементов.

Почему нет `of`/`chain`? `of(x)` должен был бы создать кортеж длины `n`, но из одного `x` непонятно, чем заполнять остальные позиции. `chain` потребовал бы «сшить» несколько кортежей, что для произвольной арности не имеет канонического смысла. Поэтому `Tuple` — функтор и полугруппа, но не аппликатив и не монада.

## 4. Почему это полезно в JavaScript

- Позиционные данные без «магических» имён: `Tuple(x, y)`, `Tuple(r, g, b)`.
- Явная арность: ошибка «передали два элемента вместо трёх» ловится сразу.
- `concat` удобен для слияния записей, где все поля — полугруппы.
- `merge` и `mapAll` дают аккуратную работу с позициями без индексов и мутаций.
- `Tuple` хорошо подходит для interop: можно быстро превратить в массив и обратно.

## 5. Границы

- Нет имён полей: `project(2)` менее читаем, чем `user.name`.
- Арность фиксирована; для коллекций переменной длины нужен массив или другой тип.
- `concat` требует полугрупп в каждой позиции и одинаковой длины — это не универсальная операция.
- В JS нет pattern matching; разбор кортежа — это `project`/`toArray`.
- `Tuple` не заменяет `Pair`: у `Pair` есть Writer-семантика, у `Tuple` — нет.

# Теория к уроку 2.1 — `Pair`

> **О чём:** как протащить рядом со значением «вторую половину» — лог, контекст, счётчик, — и почему для этого нужен моноид.
>
> Практика: [`../Урок-2.1-Pair.md`](../Урок-2.1-Pair.md)

## 1. Проблема

Функция возвращает результат, но вместе с ним хочется вернуть **сопутствующую информацию**:

- лог вычислений;
- счётчик шагов;
- предупреждения;
- контекст (например, «откуда данные»);
- несколько значений сразу.

Глобальная переменная для лога — плохо: она ломает чистоту, мешает тестам и параллелизму. Возвращать объект `{ value, log }` — уже лучше, но тогда каждую операцию нужно вручную учить объединять логи.

`Pair` — это тип-произведение из двух частей, который умеет **комбинировать** первую часть по правилу моноида, а вторую — преобразовывать как обычное значение.

## 2. История

### 2.1. Произведения в теории категорий

В категории типов произведение `A × B` — это тип пар с проекциями `fst : A × B -> A` и `snd : A × B -> B`. Объект `A × B` универсален: любая пара функций `C -> A` и `C -> B` однозначно пропускается через него.

В программировании произведение — это структура, кортеж, объект с полями. `Pair` — простейшее произведение из двух значений.

### 2.2. Writer monad

В Haskell есть монада `Writer`:

```haskell
newtype Writer w a = Writer { runWriter :: (a, w) }
```

Она позволяет накапливать «выход» `w` вдоль вычисления. Чтобы это работало, `w` должен быть **моноидом**: нужно уметь объединять два лога (`mappend`) и иметь пустой лог (`mempty`).

`Writer` — исторически одна из первых монад, которые разбирают в учебниках: она проста и хорошо показывает, зачем нужен `chain`. В `crocks` её роль играет `Pair` (а также `Writer`-подобные типы в других библиотеках).

### 2.3. От Writer к State

Есть красивая связь: `State s a` можно представить как `s -> Pair a s` — функция из состояния в пару «результат и новое состояние». То есть `Pair` — строительный блок для `State`.

## 3. Теория

```text
Pair a b
```

Первая часть (`a`) — «контекст», вторая (`b`) — «значение». Основные операции:

```text
map   :: (b -> c) -> Pair a b -> Pair a c
ap    :: Pair a (b -> c) -> Pair a b -> Pair a c
chain :: (b -> Pair a c) -> Pair a b -> Pair a c
```

- `map` меняет только вторую часть.
- `ap` и `chain` объединяют первые части через `concat`, поэтому `a` должен быть полугруппой (`Semigroup`).
- `of(x)` дал бы `Pair(empty, x)`, но для этого нужен моноид. В `crocks` `Pair.of` нет, поэтому `Pair` — это `Apply`/`Chain`, а не полноценный `Applicative`/`Monad`.
- `fst`/`snd` достают половины.

Полноценная **Writer-монада** получается, если зафиксировать моноид и добавить `of = Pair(empty, x)`. В `crocks` `Pair` даёт практическую часть этой идеи — комбинирование контекстов через `ap`/`chain`, — но без универсального `of`.

В теории `Pair w` (с фиксированным первым компонентом) — ещё и комонада, родственная `Env`: `extract` берёт вторую часть, `extend` применяет функцию к целой паре. Но в `crocks` акцент сделан на аппликативной/монадической стороне.

## 4. Почему это полезно в JavaScript

- Логирование без глобальных переменных: каждая функция возвращает `Pair(log, value)`, а `chain` собирает лог.
- Счётчики и метрики: первая часть — моноид `Sum`, вторая — результат.
- Валидация: первая часть — список предупреждений, вторая — очищенное значение.
- Объяснение вычисления: можно вернуть не только ответ, но и «как мы к нему пришли».

## 5. Границы

- Первая часть должна быть моноидом; для произвольного типа `Pair` не даст монаду.
- Лог растёт; если он большой, нужна стратегия его хранения или обрезки.
- `Pair` не заменяет нормальный логгер: он не умеет уровни, форматирование и вывод.
- В JS нет удобного pattern matching; работать с `Pair` приходится через `fst`/`snd` и методы.

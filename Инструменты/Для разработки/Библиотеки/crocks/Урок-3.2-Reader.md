# Урок 3.2 — `Reader`: вычисления с зависимостью от окружения 🔴

> Цель: научиться передавать **окружение** (конфиг, настройки, зависимости) в
> вычисления явно и лениво — без глобальных переменных и без «протаскивания»
> лишних аргументов через десять функций. Ключевые слова: `Reader(env => a)`,
> `Reader.ask`, `runWith`, `Reader.of`, `pipeK`.
> Все примеры печатают результат в консоль и проверены на crocks 0.12.
>
> Документация: https://crocks.dev/docs/crocks/Reader.html

## 1. Зачем нужен Reader

`State` (урок 3.1) умеет **читать и менять** состояние. `Reader` умеет **только
читать** — и это его сила: он описывает вычисление, которому нужно **окружение**
(конфиг, соединение с БД, логгер, настройки среды), но которое само окружение
не меняет.

Проблема, которую он решает:

```js
// конфиг приходится тащить через все слои
const getUrl = (config) => config.api + '/v1'
const fetchUser = (config, id) => request(getUrl(config) + '/users/' + id)
const handler = (config, id) => fetchUser(config, id).then(render)
// и так в каждом файле: config, config, config...
```

`Reader` инвертирует это: окружение **не передаётся** в шаги, а «подаётся» один
раз в самом конце — при запуске. Шаги просто говорят «мне нужно окружение»,
и оно материализуется в момент вызова:

```js
import crocks from 'crocks'
const { Reader } = crocks

const greet = Reader(env => 'Привет, ' + env.name)

console.log(greet.runWith({ name: 'Ivan' })) // 'Привет, Ivan'
console.log(greet.runWith({ name: 'Olga' })) // 'Привет, Olga'
```

Это и есть **dependency injection без фреймворков**: зависимости — параметр
вычисления, а не глобальная переменная.

## 2. Форма: `Reader(env => a)` и `runWith`

```js
import crocks from 'crocks'
const { Reader, runWith } = crocks

const greet = Reader(env => 'Привет, ' + env.name)

// метод
console.log(greet.runWith({ name: 'Ivan' })) // 'Привет, Ivan'

// pointfree-версия (каррирована: сначала окружение)
console.log(runWith({ name: 'Olga' })(greet)) // 'Привет, Olga'
```

> ⚠️ **`Reader` — это объект-значение, а не функция.** `typeof greet === 'object'`,
> поэтому его нельзя передать в `pipe`/`compose` (они ждут функции — урок 1.4).
> В цепочки он встраивается методами (`map`/`chain`), а «функциональная»
> композиция шагов делается через `pipeK` (раздел 7).

> ⚠️ **Чего нет в crocks 0.12 (проверено):**
> - `runReader` и `runReaderWith` из плана курса **не существуют** — запуск это
>   `runWith` (метод или pointfree-функция);
> - pointfree `run` — это **про `IO`**, не про Reader: `run(reader, env)` →
>   `TypeError: run: IO required`.

## 3. `Reader.ask()` — попросить окружение целиком

`Reader.ask()` возвращает Reader, значением которого является **всё окружение**:

```js
import crocks from 'crocks'
const { Reader } = crocks

console.log(Reader.ask().runWith(42))          // 42
console.log(Reader.ask().runWith({ a: 1 }))    // { a: 1 }

// чаще нужна функция от окружения — «asks»:
const asks = fn => Reader.ask().map(fn)

const name = asks(env => env.name)
console.log(name.runWith({ name: 'Ivan' }))    // 'Ivan'
```

> ⚠️ **`Reader.asks` в crocks 0.12 отсутствует** (проверено: `undefined`).
> В других библиотеках (`fp-ts`, `ramda-fantasy`) `asks` есть — в crocks его
> роль играет однострочная обёртка `Reader.ask().map(fn)`; её удобно объявить
> один раз в проекте.

## 4. `map`, `chain`, `ap` — и где именно «включается» окружение

```js
import crocks from 'crocks'
const { Reader } = crocks

const asks = fn => Reader.ask().map(fn)

// map — преобразовать значение, окружение доступно на этапе запуска
console.log(asks(e => e.name).map(n => n.toUpperCase()).runWith({ name: 'ivan' }))
// 'IVAN'

// chain — следующий шаг может снова спросить окружение
// ВАЖНО: chain принимает ФУНКЦИЮ a -> Reader, а не готовый Reader
const withCity = n => Reader(env => `${n} из ${env.city}`)
console.log(asks(e => e.name).chain(withCity).runWith({ name: 'Ivan', city: 'Москва' }))
// 'Ivan из Москва'

// ap — аппликатив: функция в Reader, значение в Reader
console.log(Reader.of(n => n * 2).ap(Reader.of(21)).runWith({}))
// 42
```

> ⚠️ Самая частая ошибка: `reader.chain(asks(e => e.name))`. `asks(...)` уже
> вернул **Reader**, а `chain` требует **функцию**, возвращающую Reader:
> `TypeError: Reader.chain: Function required` (проверено). Правильно:
> `chain(() => asks(...))` — если значение предыдущего шага не нужно, или
> `chain(n => Reader(env => ...))`.

## 5. Окружение неизменно и не «протекает»

`Reader` ничего не мутирует: окружение приходит параметром на каждом запуске.

```js
import crocks from 'crocks'
const { Reader } = crocks

const asks = fn => Reader.ask().map(fn)

const calc = asks(e => e.multiplier)
  .chain(m => Reader(env => env.base * m))

const env = { multiplier: 3, base: 7 }

console.log(calc.runWith(env))                       // 21
console.log(calc.runWith(env))                       // 21 — повтор стабилен
console.log(calc.runWith({ multiplier: 2, base: 100 })) // 200 — другой конфиг
console.log(env)                                      // { multiplier: 3, base: 7 } — не тронут
```

Сравни с `State` из урока 3.1: там состояние **течёт и меняется** (`execWith`
показывает новое), здесь окружение **фиксировано** на весь запуск — и это
правильно для конфигов: их не «эволюционируют» посреди вычисления.

## 6. Полный пример: сборка конфигурации

```js
import crocks from 'crocks'
const { Reader } = crocks

const asks = fn => Reader.ask().map(fn)

const buildInfo = Reader.ask()
  .map(cfg => cfg.api + '/v1')
  .chain(url => asks(cfg => `${url} (${cfg.env}: таймаут ${cfg.timeout}мс)`))

console.log(buildInfo.runWith({ env: 'prod', api: 'https://api.x', timeout: 5000 }))
// 'https://api.x/v1 (prod: таймаут 5000мс)'

console.log(buildInfo.runWith({ env: 'dev', api: 'http://localhost:3000', timeout: 1000 }))
// 'http://localhost:3000/v1 (dev: таймаут 1000мс)'
```

Один и тот же код обслуживает prod и dev: меняется только окружение. Ни одного
`if (env === 'prod')` внутри бизнес-логики — различия вынесены в конфиг.

## 7. `pipeK` — композиция «функций, возвращающих Reader»

`pipe` (урок 1.4) склеивает обычные функции `a -> b`. Для цепочек, где каждый
шаг возвращает Reader (так называемые Kleisli-функции `a -> Reader b`),
есть `pipeK`:

```js
import crocks from 'crocks'
const { Reader, pipeK } = crocks

const asks = fn => Reader.ask().map(fn)

const getName = () => asks(env => env.name)              // () -> Reader
const withDomain = n => Reader(env => `${n}@${env.domain}`) // a -> Reader

const program = pipeK(getName, withDomain)

console.log(program(undefined).runWith({ name: 'Ivan', domain: 'mail.ru' }))
// 'Ivan@mail.ru'
```

`pipeK` избавляет от вложенных `chain` — ровно то, чего не хватало в уроке 3.1.
Заодно он пригодится для `Async` в уроке 4.1 (там тоже `pipeK`).

## 8. Reader vs State: что выбирать

| | `State` (3.1) | `Reader` (3.2) |
|---|---|---|
| Окружение/состояние | **меняется** по ходу | **только читается** |
| Запуск | `runWith(s)` → `Pair(значение, состояние)` | `runWith(e)` → значение |
| Выход | `evalWith` / `execWith` / `runWith` | только `runWith` |
| Меняющие операции | `State.put` / `State.modify` | — (нет и не нужно) |
| Типичное применение | счётчики, стеки, парсеры | конфиги, DI, темы, локали |

**Правило:** если значение в ходе вычисления **изменяется** — `State`; если оно
**постоянно** и просто нужно шагам — `Reader`. Конфиг приложения — классический
`Reader`.

---

## 9. Резюме урока

| Инструмент | Роль |
|---|---|
| `Reader(env => a)` | описание вычисления, зависящего от окружения |
| `.runWith(env)` / `runWith(env)(reader)` | запуск: подставить окружение |
| `Reader.ask()` | Reader, чьё значение — всё окружение |
| `Reader.ask().map(fn)` | «asks»-эмуляция (в 0.12 отдельного `Reader.asks` нет) |
| `Reader.of(x)` | значение без зависимости от окружения |
| `.map(f)` | преобразовать значение |
| `.chain(f)`, `f: a -> Reader` | следующий шаг, который снова читает окружение |
| `.ap(m)` | аппликатив |
| `pipeK(f, g, ...)` | композиция функций `a -> Reader` |

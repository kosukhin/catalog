# `scripts/dev.ts` — режим разработки

Запуск: `npm run dev` (то же, что `node --watch scripts/dev.ts`). Обычный запуск без
перезагрузки — `npm start`.

Задача скрипта — держать в актуальном состоянии **обе** изменяемые части проекта:

| Что меняется | Что делает `npm run dev` |
|---|---|
| `server/`, `lib/`, `agents/`, `scripts/` | перезапускает процесс (`node --watch`) |
| `client/` | пересобирает бандл `server/public/physics.js` |
| `test/`, `docs/`, `README.md` | ничего |

## Как работает

1. `node --watch` (без `--watch-path`) следит за `scripts/dev.ts` и всем, что он
   импортирует **статически**;
2. скрипт статически импортирует `node:fs` и `esbuild`, а `server/index.ts`
   загружает **динамически** через `await import()`;
3. на старте бандл клиента собирается один раз, затем за `client/` следит
   `watch(...)` из `node:fs` — правка пересобирает бандл, процесс не перезапускается.

Почему именно так:

- `server/index.ts` тянет `server/config.ts` → `agents/index.ts` → всех агентов.
  Динамический `import()` не регистрирует модули в вотчере, поэтому за `server/`,
  `lib/` и `agents/` следит `esbuild`, который скрипт импортирует статически.
  Список наблюдаемых файлов остаётся маленьким, а правки тестов и документации
  сервер не перезапускают;
- `--watch-path` здесь не подходит: он **отключает** наблюдение за импортированными
  модулями и следит только за указанными путями;
- указывать `--watch-path=server` нельзя: в `server/public/` лежит собранный
  `physics.js`. Пересборка бандла — это запись файла, вотчер увидит её как правку и
  перезапустит процесс, новая сборка снова запишет файл — получается петля
  перезапусков.

Порядок важен: сначала сборка клиента, потом старт сервера — на момент открытия
дашборда `physics.js` актуален. Пересборки схлопываются паузой `REBUILD_DELAY_MS`:
сохранение нескольких файлов подряд даёт одну сборку.

## Остановка

По `SIGINT`/`SIGTERM` скрипт закрывает вотчер `client/`, снимает отложенную
пересборку и останавливает мир через `stop()` — так же, как это делают тесты
`server/index.ts`, без «висящих» потоков.

## Что видно в выводе

```
[dev] клиент собран
[dev] дашборд: http://localhost:3000 (правка client/ пересобирает бандл, правка остального перезапускает сервер)
```

Дальше идёт обычный лог мира: строки агентов вида
`[HumanAgent-1 · поток 9] …`. Перезапуск печатает обе строки `[dev]` заново;
пересборка после правки `client/` — только первую.

Если клиент не собрался (синтаксическая ошибка), скрипт пишет
`[dev] клиент не собрался, жду следующей правки` и продолжает работать — сервер и
старый бандл остаются живыми.

## Почему без дополнительных зависимостей

`node --watch` есть в Node.js 22 (проекту нужен 22.18+), `watch` — в `node:fs`,
`esbuild` уже стоит в `devDependencies` для `npm run build:client`. Поэтому отдельные
`nodemon`, `chokidar` или `concurrently` не нужны.

## Как изменить опыт

| Что | Как |
|---|---|
| не перезапускать при правках | `npm start` (сборка клиента один раз) |
| другой порт при перезапусках | `PORT=8080 npm run dev` |
| быстрее реакция на правку клиента | уменьшить `REBUILD_DELAY_MS` |

Горячей перезагрузки браузера нет: после пересборки бандла страницу `physics.html`
нужно обновить вручную.

## Тест

Отдельного юнит-теста у скрипта нет: он запускается вручную, как `scripts/demo.ts`.
Проверяется поведение сервера, который он поднимает, — `test/server-index.test.ts`
(тот же `startServer`), и сборка клиента — `test/physicsMain.test.ts`.

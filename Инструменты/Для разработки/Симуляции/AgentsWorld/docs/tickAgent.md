# `agents/tickAgent.ts` — источник импульсов времени

Агенты в этой системе пассивны: они реагируют на сообщения, но не «тикают» сами.
`TickAgent` — единственный, кто генерирует ход времени: каждые `intervalMs` он шлёт
сообщение `tick` агентам нужных **типов**.

Список получателей тикер не хранит: он спрашивает служебный реестр
(`lib/rosterAgent.ts`) — какие агенты есть в мире — и подписывается на появление
новых.

## Что экспортирует

| Экспорт | Назначение |
|---|---|
| `type` | `'TickAgent'` |
| `moduleUrl`, `createAgent` | контракт модуля агента |
| `TickAgent` | класс |
| `TICK_AGENT_ID` | `'TickAgent-1'` |
| `TickAgentOptions` | `{ intervalMs, types, rosterId }` |

Тип сообщения `tick` живёт в словаре протокола (`lib/protocol.ts`, константа
`TICK`), потому что он общий: слать может любой тикер, реагировать — любой агент.

## Настройки

| Настройка | По умолчанию | Зачем |
|---|---|---|
| `intervalMs` | 1000 | как часто рассылать импульсы |
| `types` | — (обязательна) | типы агентов, которым нужен `tick` |
| `rosterId` | `ROSTER_AGENT_ID` | у кого спрашивать адреса |

Кого будить, решает тот, кто собирает мир, — но теперь **по типу**, а не по
жёстким адресам:

```js
[agents.tickAgent, { count: 1, options: { intervalMs: 1000, types: ['HumanAgent'] } }]
```

## Как тикер находит получателей

При старте `TickAgent`:

1. шлёт реестру `roster-query` с типами — получает текущие адреса (`roster-report`);
2. шлёт реестру `roster-subscribe` с теми же типами — реестр запоминает подписчика.

На каждое `roster-update` тикер проверяет тип агента и, если тот подходит и ещё не
учтён, добавляет его к получателям. Дальше по таймеру шлёт `tick` всем накопленным
адресам. Так новый агент нужного типа начинает получать импульсы сам, без правок
конфигурации.

## Почему отдельный агент, а не таймер внутри каждого

- один таймер на мир вместо N таймеров по потокам;
- частоту меняет одно значение, а не настройки каждого агента;
- агенты остаются простыми: «пришёл `tick` — отреагировал»;
- получателей тикер не хардкодит: их даёт реестр по типам.

## Инварианты

- `types` обязателен и непуст: без него тикер не знает, кого будить.
- Пустой ответ реестра — не ошибка: тикер пока никого не будит; как только реестр
  пришлёт `roster-update`, получатели появятся.
- Одного и того же агента тикер не дублирует.
- Агенты «чужих» типов из `roster-update` игнорируются.
- `stop()` гасит таймер; повторный вызов безопасен.
- `intervalMs` — целое положительное; иначе исключение при создании.
- `describe()` отдаёт частоту, типы и число получателей — тикер виден в дашборде.

## Разложение на подмодули

| Подмодуль | Что содержит |
|---|---|
| `agents/tick/options.ts` | чтение `intervalMs`, `types`, `rosterId`, разбор ответов реестра |

Класс держит `#status` (интервал, типы, адрес реестра, таймер, получатели) и методы
`state()`, `start`, `stop`, `handle`, `describe`. Вместо геттеров
`intervalMs`/`types`/`recipientCount` — `state()`, а состояние в дашборд уходит
через `status-request` (метод `describeForDashboard` удалён).

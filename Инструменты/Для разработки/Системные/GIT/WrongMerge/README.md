# Случай: случайный мерж test → main и как его отменить

## Ситуация

Мы работаем в git-репозитории, коммитим изменения в ветку `test`. В какой-то момент
по ошибке (не та ветка, опечатка, неправильная кнопка в GUI) изменения из ветки
`test` были влиты в `main`:

```bash
# что произошло (по ошибке):
git checkout main
git merge test          # ← случайный мерж
git push origin main    # ← иногда ошибку успевают запушить в общий репозиторий
```

Теперь `main` содержит чужие/непроверенные изменения из `test`, хотя они туда
попасть не должны были.

Важно понять **до начала действий**: запушен ли мерж в общий удалённый
репозиторий и видели ли его другие люди. От этого зависит способ отката.

---

## Случай 1: мерж НЕ запушен (только локальный main)

Самый простой случай — можно просто перемотать `main` назад.

### Вариант A: `git reset --hard`

```bash
git checkout main

# посмотреть, куда нужно откатиться
git log --oneline --graph -10

# откатиться на коммит ДО мержа
git reset --hard <хэш_коммита_до_мержа>
```

Если мерж был последним действием, удобно через `ORIG_HEAD` — git сам запоминает
позицию ветки до мержа:

```bash
git reset --hard ORIG_HEAD
```

Ветка `test` при этом **не трогается** — все ваши коммиты остаются в ней.

### Вариант B: если мерж коммит ещё не создан

Если вы запустили `git merge test`, но ещё не сделали `git commit`
(или мерж был fast-forward и вы не коммитили):

```bash
git merge --abort
```

---

## Случай 2: мерж УЖЕ запушен, но никто не успел забрать (`git revert`)

Когда история уже ушла в origin, переписывать её (`reset` + `push --force`) опасно.
Правильный путь — создать **обратный коммит**:

```bash
git checkout main

# найти хэш мерж-коммита
git log --oneline --merges -5

# откатить мерж: -m 1 означает «оставляем первую родительскую ветку (main)»
git revert -m 1 <хэш_мерж_коммита>

git push origin main
```

`-m 1` — обязательный параметр для мерж-коммитов: у них два родителя, и git нужно
сказать, к какому состоянию возвращаться. `1` = родитель из `main` (то состояние,
в котором main был до мержа).

### Важный подводный камень

После `git revert -m 1` ветка `main` снова чистая, НО git «помнит», что коммиты из
`test` уже были в истории. Когда позже вы захотите слить `test` в `main`
**по-настоящему**, git скажет «Everything up-to-date» и изменения не подтянутся.

Решение — когда придёт время нормального мержа, сначала «вернуть» откаченные
коммиты:

```bash
# либо ревертнуть сам реверт
git revert <хэш_реверт_коммита>

# либо rebase ветки test на свежий main и мержить заново
git checkout test
git rebase main
git checkout main
git merge test
```

---

## Случай 3: мерж запушен, команду нужно полностью «вычистить» из истории (`reset` + force push)

Применяется только если:

- вы **уверены**, что никто не успел сделать pull/работать поверх нового main;
- репозиторий ваш личный или команда согласовала перезапись истории.

```bash
git checkout main
git reset --hard <хэш_коммита_до_мержа>
git push --force origin main
```

Более безопасный вариант, который отклонит push, если кто-то успел запушить
поверх вашего:

```bash
git push --force-with-lease origin main
```

⚠️ Никогда не делайте force push в общие защищённые ветки без согласования.

---

## Случай 4: pull request / merge request

Если `test` попал в `main` через PR/GitHub Merge button:

- **PR ещё не смёржен** — просто отклоните PR (Close / Decline) и удалите
   мерж-ветку, если создавалась.
- __PR смёржен без squash__ — откатывайте так же, как в случае 2
   (`git revert -m 1 <merge_commit>`).
- __PR смёржен через Squash merge__ — мерж-коммита нет, есть один обычный
   squash-коммит, его откатывают обычным `git revert <squash_хэш>` (без `-m 1`).

## Случай 2b: ошибочный мерж — НЕ последний коммит (реверт по хэшу)

Частая ситуация: один человек сделал ошибочный мерж `test` в `main`, а после него
другие коллеги уже успели смержить свои ветки и запушить работу. Ошибочный
мерж-коммит теперь «спрятан» в середине истории:

```
*   7ba2cc5  bob merged his feature    ← HEAD, чужой мерж ПОСЛЕ ошибочного
|\
| * 6b7ab07  bob: my feature
*   40f82f2  BAD MERGE of test         ← ошибочный мерж в середине истории
|\
| * 20e79a5  test work
* | dc74cf2  main work before accident
|/
* 68ec869   init
```

### Почему `reset` здесь НЕ подходит

`git reset --hard` перемотал бы `main` назад и **выбросил бы чужую работу**
(мерж Боба и всё, что после ошибочного мержа). А force push сломал бы репозиторий
всем, кто уже сделал pull. Когда история общая — только `revert`.

### Как сделать реверт

Найти хэш нужного мерж-коммита:

```bash
git log --oneline --graph --merges
# или с датами/авторами, чтобы точно идентифицировать:
git log --graph --merges --format="%h %ad %an %s" --date=short
```

И выполнить реверт именно этого коммита — **позиция в истории не важна**:

```bash
git revert -m 1 40f82f2
git push origin main
```

Реверт-коммит создаётся на вершине истории, но его содержимое = инвертированный
diff ошибочного мержа (разница между мерж-коммитом и его первым родителем).
Всё, что было смержено ПОСЛЕ него (работа Боба и т.д.), остаётся нетронутым.

Проверено экспериментом: после `git revert -m 1 40f82f2` изменения из `test`
удалены из main, а файлы чужих мержей (`bob.txt`) и собственные (`wrong.txt`) целы.

### Конфликты

Если коммиты, сделанные после ошибочного мержа, меняли те же строки/файлы,
`revert` может остановиться с конфликтом — это нормально:

```bash
git revert -m 1 40f82f2
# CONFLICT в some/file.txt
# разрешаете конфликт (убираете изменения test) вручную, затем:
git add some/file.txt
git revert --continue
# если всё запутались:
git revert --abort
```

Практический совет: делайте реверт как можно раньше — чем меньше коммитов
поверх ошибочного мержа, тем меньше шанс конфликта.

### Как не перепутать номер родителя

`-m` принимает номер родителя (1 или 2), а не произвольный идентификатор:

```bash
# посмотреть родителей мерж-коммита:
git show 40f82f2 --format="%P" -s
# → dc74cf2 20e79a5
#   родитель 1 = dc74cf2 (main до мержа) → -m 1 возвращает сюда
#   родитель 2 = 20e79a5 (test)          → то, что откатывается
```

`git revert <мерж>` без `-m` выдаст ошибку
*"is a merge but no -m option was given"* — git сам просит уточнить родителя.

Подводный камень тот же, что и в случае 2: после реверта повторный
`git merge test` скажет «Everything up-to-date». Для настоящего повторного
мержа — реверт реверта или rebase ветки `test` на свежий `main`.

## Шпаргалка: как выбрать способ

| Ситуация | Действие |
|---|---|
| Мерж только локально | `git reset --hard ORIG_HEAD` |
| Мерж в процессе, не закоммичен | `git merge --abort` |
| Запушен, история общая | `git revert -m 1 <merge_commit>` + push |
| Запушен, ошибочный мерж не последний (есть чужие мержи поверх) | `git revert -m 1 <хэш_мержа>` по хэшу + push, при конфликте — `--continue` |
| Запушен, никто не забрал, можно менять историю | `git reset --hard` + `push --force-with-lease` |
| PR не смёржен | Close/Decline PR |
| Squash-мерж | обычный `git revert <коммит>` |

## Профилактика

- Перед мержем: `git status` и `git branch --show-current` — убедиться, что вы на той ветке.
- Защитить `main` в настройках GitHub/GitLab (protected branch, запрет прямого push).
- Мержить через PR, а не напрямую в терминале.
- Альтернатива, если всё-таки работаете напрямую: мержить флагом `--no-ff`,
   чтобы мерж был отдельным коммитом, который легко найти и откатить.
